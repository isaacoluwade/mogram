# AI systems in the cloud: concept catalog

Stage 1 research for the **AI systems** area (see [`../README.md`](../README.md)). Researched
2026-10-05.

## 1. Scope

**In:** the system and architecture side of AI that cloud practitioners build and operate.

- How models behave as a system component: tokens, context windows, generation, reasoning models.
- The ML lifecycle and MLOps: pipelines, feature stores, experiment tracking, model registry,
  drift, retraining, shadow and A/B testing of models.
- Model serving: inference endpoints, batch vs real-time, hosting and capacity options
  (pay-per-token, provisioned throughput, self-hosted), quotas, latency (TTFT, tokens per second,
  streaming), KV cache, batching, GPU autoscaling, quantization.
- LLM application patterns: prompting, context engineering, structured output, fine-tuning vs RAG,
  embeddings, vector search (ANN/HNSW), the RAG pipeline end to end (chunking, hybrid search,
  reranking, query rewriting, permission-aware retrieval, agentic RAG), tool use, agent loops,
  workflows vs agents, multi-agent orchestration (including A2A), MCP, agent memory.
- Quality: hallucination, grounding and citations, evals, LLM-as-a-judge, RAG evaluation.
- AI-specific safety and security, and responsible AI: guardrails, prompt injection, data
  exfiltration, excessive agency, poisoning, fairness, transparency, human-in-the-loop, privacy,
  shared responsibility for AI.
- Operating LLM apps: AI gateway, model routing and fallback, semantic and prompt caching, token
  costs and budgets, LLM observability, LLMOps.
- GPU capacity and training infrastructure: accelerators, GPU capacity planning, GPU scheduling in
  Kubernetes, distributed training (data, tensor, pipeline parallelism), checkpointing on spot GPUs.

**Left to other areas:**

- **ML theory** (learning paradigms, algorithms, transformer internals, metric maths,
  overfitting): not in this catalog; see the coverage check. A candidate for a future "ML
  fundamentals" area if the library needs it.
- **Security** (`security.md`): identity, secrets, encryption, network isolation, supply-chain
  security and injection in general. This file keeps only the attacks and controls that are
  specific to LLMs and agents.
- **Containers** (`containers.md`): Kubernetes scheduling, node pools, taints, autoscalers in
  general. This file keeps the GPU-specific part.
- **Scaling** (`scaling.md`): generic caching, rate limiting, autoscaling, capacity planning.
- **Observability** (`observability.md`): logs, metrics, distributed tracing in general.
- **Delivery** (`delivery.md`): CI/CD, canary, blue/green, feature flags in general.
- **Architecture** (`architecture.md`): gateway, pipes-and-filters, fan-out/fan-in and other
  cloud design patterns.
- **Data** (`data.md`): databases, storage formats, data pipelines, data quality, search engines in
  general.
- **Platforms** (`azure.md`, `aws.md`, `gcp.md`): Microsoft Foundry and Azure OpenAI, Azure AI
  Search, the API Management AI gateway; Amazon Bedrock, SageMaker AI, Bedrock AgentCore; Gemini
  Enterprise Agent Platform (formerly Vertex AI), Model Garden, GKE Inference Gateway, TPUs.

### 3.1 Foundations: models, tokens and context

| id                    | Concept                                                        | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                    | The idea to get across                                                                                                                                  | Often confused with                                                        |
| --------------------- | -------------------------------------------------------------- | ---- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| training-vs-inference | Training vs inference                                          | 1    | any      | Training adjusts a model's weights from data (a large, occasional GPU job). Inference runs the finished model on new input to produce a prediction or text (a small job on every request, for as long as the model is in use).                                                                                                | Training is a one-off factory run; inference is the per-request running cost, and for a popular model it usually dominates spend and needs low latency. | Fine-tuning (which is more training, not inference)                        |
| foundation-model      | Foundation models and LLMs                                     | 1    | any      | A large model pre-trained on broad data that can be adapted to many tasks by prompting, retrieval or fine-tuning. LLMs work on text; multimodal models also take images or audio; small language models trade breadth for speed and cost. Open-weight models can be self-hosted; proprietary ones are reached through an API. | One general model, steered per task by its input, replaces the old pattern of training one narrow model per task.                                       | Traditional task-specific ML models; the AI service wrapped around a model |
| llm-tokens            | Tokens                                                         | 1    | any      | Models read and write text as tokens: sub-word pieces (roughly 3 to 4 characters of English) mapped to integer IDs by a tokenizer. Limits, prices, quotas and speed are all counted in tokens.                                                                                                                                | Tokens, not words or requests, are the unit of everything: context size, cost, rate limits and latency.                                                 | Words or characters; embeddings (vectors, not IDs)                         |
| context-window        | Context window                                                 | 1    | any      | The maximum number of tokens a model can consider in one call. The system prompt, conversation history, retrieved documents, tool definitions and the generated answer all share it. The model keeps nothing between calls; chat apps resend the history every turn.                                                          | The model has no memory: every call is a fresh, self-contained package that must fit a fixed token budget, and the app decides what goes in.            | Training data (what the model learned); long-term memory                   |
| next-token-prediction | How an LLM generates text (next-token prediction and sampling) | 2    | any      | An LLM produces output one token at a time: it computes a probability for every token in its vocabulary, samples one (shaped by temperature, top-p, max tokens and stop sequences), appends it and repeats.                                                                                                                   | Generation is a loop, not a lookup: output length drives response time and cost, and sampling is why the same prompt can give different answers.        | A database or search engine returning stored facts                         |
| reasoning-models      | Reasoning models and thinking tokens                           | 2    | any      | Models that generate an internal chain of thought (thinking tokens) before the final answer, usually with a configurable thinking budget or effort level. Thinking tokens are billed as output and add latency.                                                                                                               | Reasoning buys accuracy on hard multi-step problems by spending more tokens and time before answering; it's a dial to turn up only where it pays.       | Chain-of-thought prompting (asking an ordinary model to show its steps)    |

### 3.2 ML lifecycle and MLOps

| id                          | Concept                                     | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                           | The idea to get across                                                                                                                                       | Often confused with                                                                                           |
| --------------------------- | ------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| ml-lifecycle                | ML lifecycle                                | 1    | any      | The repeating loop for a predictive model: frame the business problem, collect and prepare data (features and labels), train, evaluate on held-out data, deploy, monitor, and retrain.                                                                                                                                               | It's a loop, not a line: a deployed model decays as the world changes, so monitoring feeds back into data and retraining.                                    | The software development lifecycle (code doesn't decay when data changes)                                     |
| mlops                       | MLOps: ML pipelines and continuous training | 2    | any      | Automating the lifecycle: a versioned pipeline (ingest, validate data, transform, train, evaluate, register, deploy) that runs on triggers (schedule, new data, drift, accuracy drop), with CI/CD for the pipeline code itself. Maturity runs from level 0 (manual notebooks) to level 2 (automated CI/CD plus continuous training). | In ML you ship the pipeline that produces the model, not just the model, so retraining becomes a trigger instead of a project.                               | DevOps CI/CD alone (tests code, not data or model quality)                                                    |
| feature-store               | Feature store                               | 2    | any      | A shared store of computed ML features with an offline store (full history for building training sets, point-in-time correct) and an online store (latest values at low latency for real-time inference), both fed by the same feature definitions.                                                                                  | Computing a feature once, the same way for training and serving, prevents training-serving skew and lets teams reuse features.                               | A regular database or data warehouse; a vector database                                                       |
| experiment-tracking         | Experiment tracking                         | 2    | any      | Recording each training run's code version, data version, parameters, metrics and output artifacts so runs can be compared and reproduced (MLflow is the common example).                                                                                                                                                            | If you can't say which data and settings produced a model, you can't reproduce, compare or audit it.                                                         | Model registry (holds the chosen models, not every attempt)                                                   |
| ml-model-registry           | Model registry                              | 2    | any      | A versioned catalog of trained and fine-tuned models with metadata, lineage back to the run and data, evaluation results and an approval stage; deployments pull a specific approved version.                                                                                                                                        | The registry is the hand-off between training and deployment: every production model is a named, approved, traceable version you can roll back to.           | Container registry (stores images, not model versions and their lineage)                                      |
| model-drift                 | Model drift: data drift and concept drift   | 2    | any      | Silent loss of accuracy after deployment. Data drift: the input distribution shifts (new customers, new sensors). Concept drift: the relationship between inputs and the right answer changes (fraud tactics evolve). Detected by comparing live inputs and outcomes with a training baseline.                                       | Nothing errored and the code didn't change, yet the model got worse because the world moved; only monitoring against a baseline reveals it.                  | Training-serving skew (a pipeline mismatch present from day one); a software bug                              |
| model-shadow-and-ab-testing | Shadow deployment and A/B testing of models | 2    | any      | Comparing a candidate model with the current one on real traffic. Shadow mode mirrors requests to the new model but only logs its answers; A/B testing splits users between models and compares business metrics; a canary shifts traffic gradually.                                                                                 | Offline scores don't guarantee production gains: shadow proves the new model is safe at no risk to users, A/B proves it's better on the metric that matters. | Canary or blue/green releases of app code (same mechanics, but success is model quality, not just error rate) |

### 3.3 Model serving and inference performance

| id                          | Concept                                                                   | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                                             | The idea to get across                                                                                                                                                                                 | Often confused with                                                       |
| --------------------------- | ------------------------------------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| model-inference-endpoint    | Model inference endpoint                                                  | 1    | any      | A trained model packaged, usually in a container with a serving runtime, behind an HTTPS endpoint with pre- and post-processing, running on replicas that scale with load; one endpoint can host several models or versions.                                                                                                                           | Serving a model is running a web service whose handler is a model: it needs the same scaling, health checks, auth and monitoring as any API, plus hardware the model fits on.                          | The model file itself; a training job                                     |
| batch-vs-realtime-inference | Batch, real-time and asynchronous inference                               | 1    | any      | Real-time (online) inference answers each request synchronously in milliseconds. Asynchronous inference queues large or slow requests and returns results later. Batch inference scores a whole dataset on a schedule; provider batch APIs run LLM jobs within hours at a discount.                                                                    | Choose by how soon someone needs the answer: if nobody is waiting, batch is far cheaper and simpler than keeping a low-latency endpoint warm.                                                          | Streaming responses (real-time output delivered token by token)           |
| model-hosting-options       | Model hosting options: pay-per-token, provisioned throughput, self-hosted | 2    | any      | Three ways to run a model: a shared serverless API billed per token and subject to quotas; provisioned (dedicated) throughput reserved for you at a fixed price per hour or month; or open-weight models self-hosted on your own GPU endpoints. Many teams fill provisioned capacity first and spill over to pay-per-token.                            | The choice is who pays for idle capacity: per-token suits spiky or low volume, provisioned suits steady high volume or strict latency, self-hosting adds control at the cost of running GPUs yourself. | Serverless functions (no GPUs); single-tenant hardware                    |
| llm-rate-limits             | Model quotas and rate limits (TPM and RPM)                                | 2    | any      | Providers cap usage per deployment, region or account in tokens per minute and requests per minute; excess calls get HTTP 429 with a retry-after hint. Some providers count the requested max_tokens against the quota up front.                                                                                                                       | The binding limit is usually tokens, not requests: a few long prompts can exhaust a quota that thousands of short ones wouldn't, so size max_tokens and retry with backoff.                            | Generic API rate limiting by request count                                |
| llm-latency-streaming       | LLM latency: time to first token, tokens per second and streaming         | 2    | any      | Two phases set latency. Prefill reads the whole prompt in parallel (time to first token, grows with prompt length); decode emits tokens one by one (time per output token, or tokens per second). Total time is about TTFT + TPOT x output tokens. Streaming (server-sent events) shows tokens as they are generated.                                  | Long prompts slow the start and long answers slow the finish; streaming cuts the perceived wait to TTFT, but gateways and filters must then handle partial output.                                     | Throughput (total tokens per second across all users); network latency    |
| kv-cache                    | KV cache                                                                  | 3    | any      | During generation the model keeps the attention keys and values of every token so far, so each new token doesn't recompute the whole prefix. It lives in GPU memory and grows with sequence length times concurrent requests; engines such as vLLM page it into blocks (PagedAttention) to avoid waste.                                                | GPU memory, not compute, usually caps how many conversations a server can hold at once, because each one's KV cache stays in memory until it finishes.                                                 | Prompt caching (reusing a KV cache across requests); an application cache |
| inference-batching          | Request batching for inference (continuous batching)                      | 3    | any      | Serving many requests in the same forward pass to use the GPU's parallelism. Static batching waits to fill a batch; continuous (in-flight) batching adds and removes requests at every decode step, so short answers don't wait for long ones.                                                                                                         | A GPU serving one request at a time is mostly idle; batching multiplies throughput, and continuous batching does it without making everyone wait for the slowest request.                              | Batch inference (offline scoring of a dataset)                            |
| gpu-inference-scaling       | Autoscaling and load balancing GPU inference                              | 2    | any      | Scaling model replicas on signals that reflect GPU load (queue depth, KV-cache use, tokens in flight) rather than CPU, and planning for cold starts measured in minutes (provisioning GPU nodes, pulling multi-GB weights, loading them into memory). LLM-aware load balancers route by queue length and prefix-cache affinity instead of round robin. | GPU inference doesn't scale like a web app: replicas are slow to start and requests vary enormously in cost, so scale ahead on the right signal and route by real load.                                | CPU-based horizontal pod autoscaling; round-robin load balancing          |
| model-quantization          | Quantization                                                              | 3    | any      | Storing and computing model weights (and sometimes the KV cache) at lower precision, for example 16-bit down to 8- or 4-bit, which shrinks memory and speeds inference at some loss of accuracy.                                                                                                                                                       | Fewer bits per weight lets a model fit on fewer or cheaper GPUs and run faster, in exchange for a small quality drop you must measure.                                                                 | Distillation (training a smaller model); compressing files at rest        |

### 3.4 Prompting, context and customization

| id                              | Concept                                       | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                                    | The idea to get across                                                                                                                                                                      | Often confused with                                                                                                  |
| ------------------------------- | --------------------------------------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| prompt-engineering              | Prompt engineering                            | 1    | any      | Designing the model's input: a system prompt (role, rules, output format) plus the user's message, with clear instructions, relevant context, examples (zero-, one- or few-shot), delimiters and step-by-step reasoning where useful. Reusable prompts become versioned templates with variables.                                             | The prompt is the program: specific instructions, context and examples improve output more cheaply than any other lever.                                                                    | Context engineering (choosing all the window's content, not just the wording); fine-tuning                           |
| context-engineering             | Context engineering                           | 2    | any      | Curating everything that enters the context window on each call: instructions, tool definitions, retrieved documents, history and memory, loading data just in time and compacting or summarizing old turns.                                                                                                                                  | More context isn't better: models degrade as the window fills with noise (context rot), so the job is picking the smallest set of high-signal tokens for each step.                         | Prompt engineering (the wording of instructions); buying a bigger context window                                     |
| llm-structured-output           | Structured output                             | 2    | any      | Making the model return data in a defined shape, such as JSON that matches a schema or a tool call with typed arguments, enforced by the provider's strict (constrained decoding) mode rather than by asking nicely.                                                                                                                          | When code consumes the answer, constrain the format at generation time; parsing free text with regex is a sign the structure belongs in a schema.                                           | "Reply in JSON" in the prompt (a request, not a guarantee); tool calling (same mechanism, used to request an action) |
| prompting-vs-rag-vs-fine-tuning | Prompting vs RAG vs fine-tuning               | 2    | any      | The customization ladder in rising cost and effort: prompt engineering (instructions and examples), retrieval-augmented generation (knowledge supplied at query time), fine-tuning (behavior, style or format changed by training), and rarely continued pre-training or training from scratch.                                               | Use RAG to give a model knowledge and fine-tuning to change how it behaves; try prompting first, because each step up costs more and is harder to change.                                   | Believing fine-tuning is how to teach a model new or changing facts                                                  |
| fine-tuning                     | Fine-tuning (including LoRA and distillation) | 2    | any      | Further training a pre-trained model on curated examples to specialise its behavior, tone or output format. Parameter-efficient methods such as LoRA train small adapter weights instead of the whole model, so one base model can serve many adapters. Distillation fine-tunes a small "student" model on a large "teacher" model's outputs. | Fine-tuning changes the model itself: good for consistent behavior or a cheaper specialised model, poor for fresh facts, and it creates a new model version to evaluate, host and maintain. | RAG; prompt engineering; pre-training                                                                                |

### 3.5 Embeddings, vector search and RAG

| id                 | Concept                                        | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                                                      | The idea to get across                                                                                                                                          | Often confused with                                                    |
| ------------------ | ---------------------------------------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| embeddings         | Embeddings                                     | 1    | any      | An embedding model turns text (or images or audio) into a fixed-length vector of numbers so that similar meanings land close together. Queries and documents must be embedded by the same model; changing the model means re-embedding everything.                                                                                                              | Embeddings turn meaning into geometry, so "similar" becomes "near" and can be searched with maths.                                                              | Tokens (integer IDs); encryption or hashing                            |
| vector-search      | Vector search and vector databases             | 1    | any      | Storing embeddings with their source text and metadata, then finding the vectors nearest to a query's embedding by cosine similarity, dot product or Euclidean distance. Offered by dedicated vector databases and as a feature of existing databases and search engines.                                                                                       | Vector search finds by meaning rather than matching words, so "reset my password" finds "recover account access".                                               | Keyword (full-text) search; a feature store                            |
| ann-vector-index   | Approximate nearest neighbor search (HNSW)     | 3    | any      | Exact k-nearest-neighbor search compares the query with every stored vector, too slow at scale. ANN indexes such as HNSW build a layered graph to hop quickly toward close vectors, tuned by parameters (m, efConstruction, efSearch) that trade recall against speed and memory.                                                                               | At scale you accept "almost the closest" results in exchange for orders-of-magnitude faster search, and you tune how close "almost" is.                         | Exact KNN; database B-tree indexes                                     |
| rag-pipeline       | Retrieval-augmented generation (RAG)           | 1    | any      | Two flows. Ingestion (offline): extract text from sources (including OCR and layout analysis), chunk, enrich with metadata, embed, index, and keep the index in sync as sources change or are deleted. Query (online): embed the question, retrieve the most relevant chunks, put them in the prompt with instructions, and generate an answer that cites them. | The model doesn't learn your data: you look up the relevant facts at question time and hand them over in the prompt, like an open-book exam.                    | Fine-tuning; a search engine (RAG adds generation on top of retrieval) |
| document-chunking  | Document chunking                              | 2    | any      | Splitting documents into retrievable pieces before embedding: fixed-size with overlap, by sentence or paragraph, by document structure (headings, tables, pages) or semantically, with metadata such as title, section and source attached.                                                                                                                     | Chunk size is the main RAG design knob: too small loses context, too big dilutes relevance and wastes tokens, so chunk along the document's natural structure.  | Tokenization (splitting text for the model, not for retrieval)         |
| hybrid-search      | Hybrid search                                  | 2    | any      | Running keyword (BM25 full-text) search and vector search together and merging their ranked lists, commonly with Reciprocal Rank Fusion, which combines rank positions instead of incompatible scores; often combined with metadata filters.                                                                                                                    | Vectors catch meaning and keywords catch exact terms (product codes, names, error IDs); together they miss less than either alone.                              | Reranking (a second pass over results, not a second search)            |
| rag-reranking      | Reranking                                      | 2    | any      | A second stage after retrieval: fetch a broad candidate set (say the top 50) for recall, then score each candidate against the query with a slower, more accurate model (cross-encoder, semantic ranker or LLM) and keep only the top few for the prompt.                                                                                                       | Retrieval optimises for recall, reranking for precision: cheap search casts a wide net, an expensive judge picks the best few.                                  | Hybrid search fusion; sorting by date or popularity                    |
| query-rewriting    | Query rewriting and decomposition              | 3    | any      | Transforming the question before retrieval: rewriting vague questions, adding context from the conversation, splitting a compound question into sub-queries, or generating a hypothetical answer and embedding that instead (HyDE).                                                                                                                             | Users ask in ways documents don't phrase things; reshaping the question to resemble the answer you want improves what retrieval finds.                          | Prompt engineering of the final answer                                 |

### 3.7 Quality: hallucination, grounding and evaluation

### 3.8 Safety, security and responsible AI

| id                        | Concept                                | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                                                                                                         | The idea to get across                                                                                                                                                        | Often confused with                                                                                                            |
| ------------------------- | -------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| ai-guardrails             | Guardrails and content filtering       | 2    | any      | Checks wrapped around the model on the way in and out: harmful-content classifiers (hate, violence, sexual, self-harm), prompt-attack detection, denied topics, PII detection and redaction, blocklists, and output checks such as groundedness and format validation.                                                                                                                                             | The model's own training isn't your policy; guardrails are separate, configurable layers you control on both input and output.                                                | The model's built-in refusals; authentication and authorization                                                                |
| prompt-injection          | Prompt injection (direct and indirect) | 1    | any      | Input that overrides the developer's instructions. Because the model can't reliably separate instructions from data, its output must be treated as untrusted before it reaches other systems. | To an LLM any text it reads can act as instructions, so every document, page and tool result is a possible attacker; limit what the model can do rather than hoping it obeys. | SQL injection (fixable by parameterization; prompt injection has no complete fix); jailbreaking (one kind of direct injection) |
| llm-data-exfiltration     | Data exfiltration through LLM apps     | 2    | any      | Sensitive data leaking via the model. | excessive-agency          | Excessive agency and agent permissions | 2    | any      | Giving an LLM or agent more tools, permissions or autonomy than the task needs, so a mistake or an injection becomes real damage (deleted records, sent emails, executed code). | data-and-model-poisoning  | Data and model poisoning               | 3    | any      | Corrupting what a model learns from or reads: tampered training or fine-tuning data that plants biases or backdoors, malicious model files from public hubs, or planted documents in a RAG index or an agent's memory.                                                                                                                                                                                             | Whatever a model learns from or retrieves becomes part of its behavior, so data sources and model artifacts need the same provenance checks as code.                          | Prompt injection (attacks at query time, not stored data)                                                                      |
| responsible-ai-principles | Responsible AI principles              | 1    | any      | Commonly stated as fairness, reliability and safety, privacy and security, inclusiveness, transparency (explain how the system works and why it decided, disclose AI use, publish model cards) and accountability (people answer for outcomes), turned into requirements, reviews and technical controls across the lifecycle.                                                                                     | Responsible AI is engineering, not a slogan: each principle maps to controls you design, measure and monitor.                                                                 | Legal compliance alone; content filtering alone                                                                                |
| ai-bias-fairness          | Bias and fairness in AI systems        | 2    | any      | Systematic differences in outcomes across groups, introduced by unrepresentative or historically biased data, labeling, proxies for protected attributes or feedback loops; measured by comparing metrics per subgroup and reduced through data, model and process changes.                                                                                                                                        | A model trained on biased history automates that bias at scale, and overall accuracy hides it; only measuring per group shows it.                                             | Statistical bias and variance in model fitting                                                                                 |
| human-in-the-loop         | Human-in-the-loop                      | 2    | any      | Points where people review, approve or correct AI work: approval gates before high-impact agent actions, review queues for low-confidence predictions, escalation to a person, and feedback captured for evaluation and retraining.                                                                                                                                                                                | Put people where errors are costly or irreversible, not on everything; the system routes work to review by risk and confidence.                                               | Manual operation (no automation); people only labeling training data                                                           |
| ai-data-privacy           | Data privacy for AI                    | 2    | any      | Controlling what personal or confidential data flows into prompts, logs, fine-tuning sets and indexes: the provider's retention and training-use terms, where inference is processed (regional vs global deployments), private network access to model endpoints, PII redaction before sending, and treating prompt and response logs as sensitive data.                                                           | Every prompt is data leaving your boundary: know where it's processed, whether it's stored or trained on, and who can read the logs.                                          | Model security (attacks on the model)                                                                                          |
| ai-shared-responsibility  | Shared responsibility for AI workloads | 2    | any      | Who secures and governs what depends on how you consume AI: using a SaaS AI app, calling a provider's model API, building an app on it, fine-tuning, or self-hosting or training your own model (for example the five scopes of the AWS Generative AI Security Scoping Matrix). ### Deliberately left out across all sources

- **ML theory**: learning paradigms, algorithms, transformer and attention internals, diffusion,
  overfitting, bias-variance, class imbalance, convergence, ensembles, metric formulas,
  hyperparameter tuning, AutoML. The brief asks for the system side; these would form a separate
  "ML fundamentals" area if wanted.
- **Model-producer work**: pre-training from scratch, RLHF and preference tuning. Named inside
  fine-tuning and prompting-vs-rag-vs-fine-tuning for context only.
- **Modality-specific services**: vision, OCR products, speech, translation, image and video
  generation. These are product catalogs for the platform files.
- **Inference-engine internals**: speculative decoding, disaggregated prefill and decode, operator
  fusion, FlashAttention. Invisible to most operators; prefill and decode are explained within
  llm-latency-streaming. Candidates for tier-3 additions if the serving plans need them.
- **Edge and on-device inference**: niche for this library, and removed from MLA-C02.
- **Legal and policy frameworks** (EU AI Act, NIST AI RMF, ISO/IEC 42001, IP law): policy rather
  than mechanisms; responsible-ai-principles and ai-shared-responsibility carry the system side.
- **Folded rather than separate** (to avoid near-duplicates): model selection (into
  model-routing-and-fallback), distillation and LoRA (fine-tuning), A2A (multi-agent-orchestration),
  GPU sharing via MIG and time-slicing (gpu-scheduling-kubernetes), GPU cluster interconnects
  (distributed-training), explainability and model cards (responsible-ai-principles), spillover from
  provisioned to pay-per-token (model-hosting-options and model-routing-and-fallback), inference
  parameters (next-token-prediction), streaming (llm-latency-streaming), budgeting
  (llm-token-costs), prompt versioning (llmops).
