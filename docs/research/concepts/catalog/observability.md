# Observability

Stage 1 catalog: 61 concepts (16 tier 1, 37 tier 2, 8 tier 3) in 12 groups.

## Scope

**In:** understanding a running system from the telemetry it emits. That covers: monitoring vs
observability; the signals (logs, metrics, traces, profiles, events) and when to use each;
logging practice; the metric data model, metric types, cardinality, aggregation, percentiles and
collection; distributed tracing and context propagation; OpenTelemetry; the monitoring methods
(golden signals, RED, USE); designing alerts, including alerting on SLOs (burn rate); dashboards;
health checks, heartbeats, synthetic and real-user monitoring; continuous profiling and eBPF;
correlating signals and debugging in production with wide events; and the cost of telemetry.

**Left to other areas:**

- **Reliability:** defining SLIs, SLOs, error budgets and SLAs; incident response, on-call,
  runbooks, postmortems; failover. Observability owns _alerting on_ SLOs (burn rate) and the
  measurement plumbing underneath them.
- **Security:** SIEM, threat detection, cloud audit trails as a security control, log integrity
  for compliance. Observability keeps only the audit-vs-application log distinction and keeping
  PII out of telemetry.
- **Scaling:** tail-latency amplification under fan-out, capacity planning, autoscaling on
  metrics, load testing. Observability owns how latency is _measured_ (percentiles, histograms).
- **Containers:** Kubernetes liveness/readiness/startup probes, the cluster monitoring stack
  (kube-state-metrics, metrics-server, Prometheus/OTel operators), container log plumbing.
- **Networking:** load-balancer health probes, flow logs, packet capture, service-mesh telemetry.
- **Data:** time-series and columnar databases as storage engines.
- **Delivery:** automated canary analysis, deployment verification, feature flags, monitoring
  configuration as code.
- **Messaging:** queue semantics; tracing through queues appears here only as span links.
- **AI systems:** LLM and agent observability (prompt/response traces, token usage, evals).
- **Fundamentals:** watching the cloud bill (FinOps). Here, only the cost _of_ telemetry.
- **Azure / AWS / Google Cloud:** each platform's monitoring, logging, tracing, profiling and APM
  services (listed under Overlaps).

| monitoring-vs-observability | Monitoring vs observability                | 1    | any      | Monitoring checks a system against conditions you predicted in advance: dashboards and threshold alerts for known failure modes. Observability is being able to ask _new_ questions of the telemetry and explain behaviour you didn't predict, without shipping new code to do it.      | Monitoring tells you _that_ something is wrong with a failure mode you already knew about. Observability tells you _why_, and for whom, including failure modes nobody has seen before. You need both: monitoring tells you where to look, and observability lets you find the cause.                                                                              | APM; "having the three pillars" (owning a logs tool, a metrics tool and a tracing tool doesn't make a system observable) |
| telemetry-signals           | The telemetry signals and when to use each | 1    | any      | The kinds of data a system emits. Metrics are cheap numeric aggregates over time. Events are discrete occurrences such as a deploy. | Each signal answers a different question at a different cost. Metrics tell you _that_ something changed and are cheap enough to alert on. Traces tell you _where_ in the request path it happened. Logs and events tell you _exactly what_ happened. Profiles tell you _which line of code_. Start from a metric, narrow it down with a trace, confirm with a log. | Treating logs, metrics and traces as interchangeable "pillars"                                                           |

Usually buffered so that it doesn't block or crash the application.                      | Telemetry is data with a supply chain. A pipeline between your apps and your backends lets you enrich, scrub, sample, reroute, or fan out to a new vendor without touching application code. Every stage is also a place to control cost and quality.                                                                                                              | The observability backend itself                                                                                         |

### Logs

| id                             | Concept                        | Tier | Platform | What it is                                                                                                                                                                                                                                                                | The idea to get across                                                                                                                                                                                                                                                | Often confused with                                                                  |
| ------------------------------ | ------------------------------ | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| structured-logging             | Structured logging             | 1    | any      | Writing each log entry as key/value fields (usually JSON) with consistent names, instead of a free-text sentence.                                                                                                                                                         | A log line is data, not prose. `{"event":"payment_failed","order_id":123,"latency_ms":840}` can be filtered, counted and grouped. "Payment failed for order 123 after 840ms" has to be parsed with a regex, and the parsing breaks when someone rewords the message.  | Pretty-printed or formatted logs                                                     |
| log-levels                     | Log levels                     | 1    | any      | Severity labels on each entry (TRACE, DEBUG, INFO, WARN, ERROR, FATAL). They let you filter both when a line is emitted and when you query.                                                                                                                               | Levels are a volume dial. Production usually runs at INFO and drops DEBUG at the source, so the level you pick decides whether a line will even exist when you need it. ERROR should mean someone needs to act, not just that something unusual happened.             | Alert severity (a log level is not an alert)                                         |
| log-aggregation                | Log aggregation                | 1    | any      | Shipping logs from every instance to one central, searchable store. Apps write to stdout or files, a node agent (Fluent Bit, the OTel Collector) tails and forwards them, a pipeline parses and enriches them, and a backend indexes them.                                | Cloud instances are numerous and short-lived. Logs left on the machine disappear with it and can't be searched together. Centralise them first, and one query can then cover every replica, including replicas that no longer exist.                                  | Log retention; SIEM                                                                  |
| correlation-ids                | Correlation IDs                | 1    | any      | A unique ID assigned where a request enters the system. It's passed to every downstream call and written into every log line. Today it's usually the W3C trace ID.                                                                                                        | Without a shared ID, the logs for one user's failed checkout are scattered across ten services among millions of lines. With one, a single filter puts the whole story back together across every service.                                                            | Session ID or user ID (these identify a person, not one request)                     |
| pii-in-logs                    | PII and secrets in telemetry   | 2    | any      | Personal or secret data (emails, card numbers, tokens, passwords) ending up in logs, span attributes, baggage or metric labels. The controls: don't log it, mask or redact it at the source or in the pipeline, restrict who can access it, and limit how long it's kept. | Telemetry gets copied everywhere: to agents, pipelines, vendors and backups, often with broad engineer access and long retention. A token logged once is as good as published. Redact as early as possible. A scrubber in the pipeline is a backstop, not the plan.   | Encryption at rest (encrypted logs still show PII to everyone allowed to query them) |
| log-based-metrics              | Log-based metrics              | 2    | any      | Counting or measuring the log entries that match a pattern as they're ingested, producing a time series (errors per minute, a latency pulled out of a field) that can be graphed and alerted on.                                                                          | Logs are expensive to keep and slow to scan. A metric derived at ingest is cheap, fast, and outlives the logs it came from. You can alert on something only the logs know about without rescanning raw logs every minute.                                             | Scheduled log queries used as alerts                                                 |
| audit-logs-vs-application-logs | Audit logs vs application logs | 2    | any      | Audit logs record who did what to which resource, when, and from where. They cover security-relevant actions and are often immutable and kept for years. Application logs record what the software did, for debugging. They're kept briefly and can be sampled freely.    | They look alike but follow opposite rules. Application logs can be sampled, dropped and expired to save money. Audit logs must be complete, tamper-evident, access-controlled, and kept for as long as compliance requires. Mixing the two in one stream breaks both. | Access logs (HTTP request logs)                                                      |

### Metrics

| id                             | Concept                                                         | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                                                                     | The idea to get across                                                                                                                                                                                                                                                                                                                                       | Often confused with                                                                            |
| ------------------------------ | --------------------------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| metric-time-series             | Metrics as labelled time series                                 | 1    | any      | A metric is a named stream of (timestamp, value) samples. Labels (dimensions) such as `service`, `region` and `status` split it, and each unique combination of name and labels is a separate time series.                                                                                                                                                                     | `http_requests_total{service="cart",status="500"}` is one series. Change any label value and you have a new one. Labels are what let you slice ("errors by region"), and they're also what multiplies storage.                                                                                                                                               | Log events (a metric discards the individual event and keeps only the aggregate)               |
| metric-types                   | Metric types: counter, gauge, histogram, summary                | 1    | any      | A counter only goes up and resets on restart (requests served). A gauge is a current value that rises and falls (queue depth, memory in use). A histogram counts observations into buckets (latency). A summary reports quantiles computed on the client. OpenTelemetry adds UpDownCounter and asynchronous variants, and can send counters as cumulative totals or as deltas. | Pick the type from the question you're asking. A counter is graphed as a _rate_: its raw value mostly tells you how long the process has been up, and it survives missed scrapes. A gauge is a snapshot and can't be added up over time. A histogram keeps the shape of the distribution. The wrong type gives quietly wrong graphs.                         | Counter vs gauge (a "requests since last scrape" gauge loses data whenever a scrape is missed) |
| latency-percentiles            | Latency percentiles (p50, p95, p99)                             | 1    | any      | Describing latency by percentiles instead of the average. The p99 is the value that 99% of requests are faster than.                                                                                                                                                                                                                                                           | Averages hide pain. A 120 ms mean can sit on top of 1% of requests waiting 5 seconds. The p99 is what your unluckiest regular users experience, and at scale 1% is thousands of people. Apdex is an older single-score alternative.                                                                                                                          | Average latency; the SLO target (a percentile is a measurement, an SLO is a promise)           |
| percentiles-from-histograms    | Percentiles from histograms (and why summaries don't aggregate) | 2    | any      | Computing percentiles on the server from histogram bucket counts (e.g. `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))`), instead of having each instance report percentiles it has already computed (a summary).                                                                                                                      | You can't average percentiles: the mean of ten servers' p99s is not the fleet's p99. Bucket counts _can_ be added across instances and over time, with the percentile computed once at the end. That's why histograms aggregate and summaries don't. Accuracy depends on where the bucket boundaries fall. Native (exponential) histograms fix most of that. | Summary metrics; averaging each instance's p99                                                 |
| metric-cardinality             | Metric cardinality and cardinality explosions                   | 2    | any      | The number of distinct time series a metric produces: the number of values of each label, multiplied together. Tools fight it with cardinality limits and by dropping labels (OTel Views, relabelling).                                                                                                                                                                        | Cardinality multiplies, it doesn't add. 20 endpoints × 5 status codes × 50 pods is 5,000 series. Add `user_id` and it becomes millions, each costing memory and money. Values with no upper bound (user IDs, request IDs, raw URLs) belong in traces and logs, not in metric labels.                                                                         | High-cardinality analysis on events (there it's the point, here it's a cost)                   |
| metric-aggregation-and-rollups | Aggregation and rollups                                         | 2    | any      | Reducing metric data across dimensions (sum per-pod series into one per-service series) and across time (downsample 10-second samples into 5-minute or hourly rollups), often precomputed with recording rules.                                                                                                                                                                | Aggregation only goes one way. Once you've summed away the `pod` label or rolled up to hourly values, the detail is gone for good. Keep raw resolution for the short term and rollups for the long term. Roll up with the right function: sum counters, use max or a percentile for latency, and never average averages.                                     | Sampling (sampling drops whole events; aggregation merges them)                                |
| push-vs-pull-collection        | Push vs pull collection (scraping)                              | 2    | any      | Two ways metrics reach a backend. In pull, the monitoring system discovers targets (service discovery) and scrapes each one's metrics endpoint on an interval, as Prometheus does. In push, the app or an agent sends metrics to a collector (StatsD, OTLP, or Prometheus's Pushgateway for batch jobs).                                                                       | Pull makes the monitor the judge of whether a target is alive: a failed scrape (`up == 0`) is itself a signal, and targets don't need to know where the monitor is. Push suits short-lived jobs, serverless functions, and sources behind firewalls that can't be scraped. Most real setups use both.                                                        | Push notifications (alerts)                                                                    |
| exemplars                      | Exemplars                                                       | 3    | any      | A sample trace ID attached to a metric data point or histogram bucket. A point on a latency graph then links to one real request that contributed to it.                                                                                                                                                                                                                       | Exemplars bridge "p99 spiked at 14:02" to "here's a request that was slow at 14:02". One click takes you from an aggregate to a concrete trace, without putting trace IDs into labels (which would explode cardinality).                                                                                                                                     | Metric labels holding trace IDs                                                                |

### Distributed tracing

| id                     | Concept                              | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                | The idea to get across                                                                                                                                                                                                                                                                                                         | Often confused with                                                           |
| ---------------------- | ------------------------------------ | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| distributed-tracing    | Distributed tracing                  | 1    | any      | Recording the journey of one request through every service, queue and database it touches as a single trace: a tree of timed spans, usually shown as a waterfall (Gantt) chart.                                                                                                                                           | A trace turns "checkout is slow" into "checkout spent 1.8 of its 2 seconds waiting on the inventory service's third database call". The waterfall shows which calls run one after another and which run in parallel, where the gaps are, and where an error started.                                                           | Logging (logs belong to one process; a trace connects them across processes)  |
| trace-span             | Spans and parent/child relationships | 1    | any      | A span is one timed operation within a trace. It has a name, a start and end time, the trace ID, its own span ID and its parent's span ID. It also has a kind (server, client, producer, consumer, internal), attributes, timestamped span events, and a status (unset, ok, error).                                       | The parent ID is what turns a pile of spans from different machines into a tree. Each service records its own spans and sends them separately, and the backend rebuilds the request by following the parent links. The span with no parent is the root, and its duration is what the user experienced.                         | A log line (a span has a duration and a place in a tree)                      |
| context-propagation    | Context propagation                  | 2    | any      | Carrying trace context (trace ID, current span ID, sampling decision) from one unit of work to the next. Within a process it travels in a context object. Between processes it's _injected_ into HTTP headers or message metadata and _extracted_ on the receiving side.                                                  | Tracing only works if every hop passes the context along. One service, proxy or queue that drops the headers splits the trace in two, and the backend can't stitch it back together. That's why instrumentation for HTTP clients and messaging libraries matters so much.                                                      | Baggage (application data riding on the same mechanism)                       |
| w3c-trace-context      | W3C Trace Context (`traceparent`)    | 2    | any      | The W3C-standard headers for trace context. `traceparent` holds version, trace ID, parent ID and flags (e.g. `00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`). `tracestate` holds vendor-specific key/values.                                                                                                   | A shared header format lets a request traced by one vendor's agent carry on through another vendor's. Each hop keeps the trace ID, swaps the parent ID for its own span ID, and honours or re-decides the sampled flag. Public edges shouldn't blindly trust an incoming sampled flag, or callers can force expensive tracing. | B3 and other vendor headers (older, incompatible formats); the baggage header |
| baggage-propagation    | Baggage                              | 3    | any      | Application-defined key/values (tenant ID, customer tier, experiment) propagated with the trace context to every downstream service in the W3C `baggage` header. Code there can read them and copy them onto spans, logs or metrics.                                                                                      | Baggage lets a service deep in the call chain know something only the edge knew ("this is a premium customer") without changing every API in between. It isn't recorded automatically, though. It travels in plain headers and can leak to third parties unless it's stripped at the boundary.                                 | Span attributes (recorded on one span, never propagated)                      |
| span-links             | Span links                           | 3    | any      | A reference from a span to spans in other traces that caused it. Used when an operation has many causes: a batch consumer processing 100 queued messages, fan-in, a scheduled job triggered by earlier work.                                                                                                              | Parent/child assumes each operation has one cause. Asynchronous work breaks that assumption, because a batch has 100 parents. Links keep each message's original trace reachable without forcing everything into one giant trace.                                                                                              | Parent/child relationships                                                    |
| trace-sampling         | Trace sampling: head vs tail         | 2    | any      | Keeping only some traces. Head sampling decides when the request starts (e.g. keep 10%, chosen deterministically from the trace ID) and propagates that decision downstream. Tail sampling buffers every span of a trace and decides once it completes (keep all errors and slow traces, plus a few percent of the rest). | Head sampling is cheap and consistent, but blind: it decides before anyone knows whether the request will fail. Tail sampling keeps the interesting traces, but it needs a stateful collector tier that sees every span of each trace. Record the sample rate on what you keep so counts can be scaled back up.                | Metric aggregation; filtering by log level                                    |
| service-map            | Service maps                         | 2    | any      | A graph of services and their dependencies, with request rate, error rate and latency on each edge. It's built automatically from the client and server spans in traces.                                                                                                                                                  | Nobody's architecture diagram is up to date. A service map is drawn from what actually called what in the last hour. It shows how far a failing dependency's damage spreads, and surprises like a service still calling an API that was supposedly retired.                                                                    | An architecture diagram (the intended design, not observed traffic)           |
| critical-path-analysis | Critical path analysis               | 3    | any      | Finding the chain of spans in a trace that actually set the end-to-end latency: the longest dependent path, leaving out work that ran in parallel with it. Across many traces, it ranks which services are most often on that path (e.g. Uber's CRISP).                                                                   | Making a span faster only helps if it's on the critical path. A 300 ms call running in parallel with a 900 ms call can be optimised and nothing changes. Shave the 900 ms call and the whole request gets faster.                                                                                                              | The slowest span; total time spent in a service                               |

### OpenTelemetry

| id                             | Concept                                                      | Tier | Platform | What it is                                                                                                                                                                                                                                                                                                                            | The idea to get across                                                                                                                                                                                                                                                                                                    | Often confused with                                                               |
| ------------------------------ | ------------------------------------------------------------ | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| opentelemetry                  | OpenTelemetry (OTel)                                         | 1    | any      | The CNCF open standard for producing and moving telemetry: a specification, per-language APIs and SDKs, instrumentation libraries, the OTLP wire protocol and the Collector. It covers traces, metrics and logs, with profiles in alpha. It is not a backend: it doesn't store or display anything.                                   | Instrument once, send anywhere. Telemetry produced with OpenTelemetry can go to any backend (Prometheus, Jaeger, a vendor, a cloud service) by changing configuration, not code. Switching observability vendor becomes a settings change instead of a rewrite.                                                           | An observability backend or vendor; OpenTracing and OpenCensus (its predecessors) |
| otel-api-vs-sdk                | OTel API vs SDK                                              | 3    | any      | OpenTelemetry separates the API (interfaces for creating spans and recording metrics, which do nothing on their own) from the SDK (the implementation that samples, batches and exports). Libraries depend only on the API. The application installs and configures the SDK.                                                          | A library can be instrumented once and cost nothing for users who don't want telemetry, because without an SDK the API is a no-op. The application owner, not the library author, decides sampling, exporters and destinations.                                                                                           | Instrumentation libraries; exporters                                              |
| auto-vs-manual-instrumentation | Automatic (zero-code) vs manual (code-based) instrumentation | 2    | any      | Zero-code instrumentation hooks into frameworks and libraries (via a language agent, bytecode or monkey patching, or eBPF) and emits spans and metrics for HTTP, database and messaging calls without code changes. Code-based instrumentation adds your own spans, attributes and metrics through the API.                           | Auto-instrumentation gives you the skeleton of every request in minutes: the edges where your code talks to the outside world. Only manual instrumentation adds the business meaning (cart size, customer tier, which feature flag) that actually explains a problem. Use both.                                           | "Automatic" meaning "complete"                                                    |
| otel-collector                 | The OpenTelemetry Collector                                  | 2    | any      | A vendor-neutral process that receives, processes and exports telemetry to one or more backends. It runs as an _agent_ next to each app or node (sidecar or DaemonSet), as a central _gateway_ tier, or as both.                                                                                                                      | Apps hand their telemetry off quickly to a nearby collector and get back to work. The collector handles batching, retries, enrichment, redaction, sampling and routing. Agents gather data locally. Gateways apply central policy: tail sampling, credentials, controlling egress.                                        | The OTel SDK; the backend                                                         |
| otel-collector-pipeline        | Collector pipelines: receivers, processors, exporters        | 2    | any      | The Collector's configuration model is a pipeline per signal. Receivers take data in (OTLP, Prometheus scrape, filelog). Processors change it (batch, memory_limiter, attributes, filter, tail_sampling, Kubernetes metadata). Exporters send it on. Connectors join pipelines together, for example deriving RED metrics from spans. | Telemetry moves along a declared assembly line: in, transform, out. Changing what you collect, how you scrub or sample it, and where it goes means editing configuration in one place, not redeploying every service.                                                                                                     | Single-signal log shippers; ETL                                                   |
| otel-semantic-conventions      | Semantic conventions and resource attributes                 | 2    | any      | Standard names and values for attributes that describe common operations (`http.request.method`, `http.response.status_code`, database and messaging attributes) and for the _resource_ that emitted the telemetry (`service.name`, `service.version`, `k8s.pod.name`, cloud region).                                                 | If every team names the same thing differently (`status`, `http_code`, `statusCode`), no dashboard, query or vendor feature works across services. Shared names, plus resource attributes saying which service, version and pod produced each signal, are what make telemetry joinable and let tools work out of the box. | Metric labels and tags in general (conventions are the agreed names for them)     |

### Monitoring methods

| id                  | Concept                   | Tier | Platform | What it is                                                                                                                                                                                                                                                                                          | The idea to get across                                                                                                                                                                                                                                                                      | Often confused with                                                    |
| ------------------- | ------------------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| four-golden-signals | The four golden signals   | 1    | any      | Google SRE's minimum set to monitor for any user-facing system. Latency, with successful and failed requests kept separate. Traffic: the demand on the system. Errors: the rate of failed requests, whether explicit, implicit or by policy. Saturation: how full the most constrained resource is. | If you can only measure four things, measure these. Latency and errors describe what users experience, traffic shows how much is being asked of the system, and saturation shows how close it is to falling over. Fast failures can make latency look _better_, so measure them separately. | RED method; USE method                                                 |
| red-method          | The RED method            | 2    | any      | Tom Wilkie's per-service method for request-driven services: Rate (requests per second), Errors (failed requests per second) and Duration (the distribution of request latency).                                                                                                                    | Every microservice gets the same three graphs, so anyone on call can read any service's dashboard and compare services with each other. RED is the caller's view of a service. It tells you something is wrong, not which resource is to blame.                                             | USE method; the four golden signals (RED leaves out saturation)        |
| use-method          | The USE method            | 2    | any      | Brendan Gregg's method for resources (CPUs, memory, disks, network interfaces, and software resources such as thread pools and locks). | business-metrics    | Business metrics and KPIs | 2    | any      | Metrics for what the system exists to do: orders per minute, sign-ups, payments succeeded, messages delivered. | alert-rules                        | Alert rules and the alert lifecycle    | 1    | any      | A rule (a query plus a condition) evaluated on a schedule against telemetry. | pages-vs-tickets                   | Pages vs tickets                       | 2    | any      | Routing by urgency. | alert-routing-and-escalation       | Alert routing, grouping and escalation | 2    | any      | The notification side of alerting. ### 10. The brief's own topic list

Everything in the brief has a home. Two items were folded rather than given their own row:
**log sampling** is in observability-cost and trace-sampling (same mechanics: keep errors, sample
successes, record the rate), and **scraping** is in push-vs-pull-collection. Uptime checks are in
synthetic-monitoring. Meta-monitoring and dead man's switches are in health-checks-and-heartbeats.
Other things deliberately left out:

- **Dynamic instrumentation / live debugging** (non-breaking breakpoints, snapshot debuggers): niche
  vendor tooling, and Google's Cloud Debugger has been retired.
- **Query languages** (PromQL, LogQL, KQL): tool syntax. KQL belongs in azure.md.
- **Observability maturity models, build vs buy:** organisational, not system concepts.
