# Data & storage: concept catalog

Stage 1 research for the **Data** area: databases, transactions, consistency, replication,
partitioning, storage, analytics, backup and schema change.

## Scope

**In scope.** How data is stored, kept correct, kept safe and moved:

- Storage types and their economics: block, file and object storage; redundancy; tiers; lifecycle;
  durability; erasure coding; versioning, soft delete and immutability.
- Data shapes and modelling: structured vs unstructured, relational model, normalization,
  schema-on-read, NoSQL access-pattern design, materialized views, multi-tenant data isolation.
- Database families: relational, key-value, document, wide-column, graph, time-series, search,
  vector, distributed SQL.
- Transactions: ACID, isolation levels and each anomaly, MVCC, serializability, locking,
  deadlocks, two-phase commit.
- Distributed data: replication (leader-follower, multi-leader, leaderless), quorums, failover,
  split brain, consensus, geo-replication; CAP, PACELC and the consistency models.
- Partitioning: sharding, range vs hash, hot partitions and skew, consistent hashing,
  rebalancing, secondary indexes in a sharded store.
- Storage engines and query performance: indexes, B-tree vs LSM-tree, write-ahead log, query
  plans, N+1 queries, connection pooling.
- Analytics: OLTP vs OLAP, warehouse, lake, lakehouse, open table formats, medallion, data mesh,
  columnar storage, partitioned tables, dimensional modelling, ETL/ELT, CDC, incremental loads,
  orchestration, MapReduce and Spark-style processing, stream windowing and watermarks,
  catalog/lineage, data quality.
- Backup and recovery mechanics: backup types, snapshots, point-in-time restore, backup vs
  replication.
- Schema evolution and migration: migrations, expand/contract, online schema change,
  backward/forward compatibility, database migration with CDC cutover.

**Left to other areas** (see Overlaps for the full list):

- **Scaling**: caching mechanics (cache-aside, read-through, write-through, write-behind, TTL and
  invalidation, stampede), vertical vs horizontal scaling, latency percentiles, throttling.
- **Reliability**: RPO/RTO, disaster-recovery strategies (backup-restore, pilot light, warm
  standby, active-active), restore testing, general failover and redundancy.
- **Messaging**: queues, pub/sub, log-based brokers (Kafka), delivery guarantees and exactly-once,
  idempotent consumers, transactional outbox, sagas, schema registry.
- **Architecture**: event sourcing, CQRS, the cloud design pattern catalogue as patterns,
  noisy neighbour, deployment stamps, unreliable networks and partial failure in general.
- **Security**: encryption at rest and in transit, key management, row/column-level security,
  dynamic data masking, PII discovery, right to erasure, data residency, presigned URLs/SAS.
- **AI systems**: embeddings, vector search algorithms (ANN, HNSW, IVF), RAG.
- **Containers**: persistent volumes, StatefulSets, etcd.
- **Delivery**: running migrations in pipelines, CI/CD for data pipelines.
- **Observability**: database and pipeline monitoring, slow-query logs, audit logs.
- **Platform files**: each cloud's own services and settings (Cosmos DB consistency levels,
  DynamoDB keys and indexes, Aurora storage, BigQuery slots, Spanner TrueTime, S3/Blob/GCS classes,
  LRS/ZRS/GRS, Fabric, Redshift, Synapse and so on), listed under Overlaps.

### 1. Storage types, redundancy and lifecycle

| id                         | Concept                                   | Tier | Platform | What it is                                                                                                                                                       | The idea to get across                                                                                                                                                                        | Often confused with           |
| -------------------------- | ----------------------------------------- | ---- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| block-storage              | Block storage                             | 1    | any      | A raw virtual disk made of fixed-size blocks, attached to one machine that formats it with its own file system. Sized by capacity, IOPS and throughput.          | It's a hard drive plugged into one server: fast and low-latency, but only that server's operating system knows what's on it.                                                                  | File storage                  |
| file-storage               | File storage                              | 1    | any      | A shared file system of folders and files served over the network (SMB or NFS) and mounted by many machines at once.                                             | Many machines see the same folders, with locks and permissions, so existing applications work unchanged.                                                                                      | Block storage; object storage |
| object-storage             | Object storage                            | 1    | any      | Whole objects (bytes plus metadata) stored under a key in a bucket or container, reached over an HTTP API, in a flat namespace with practically unlimited scale. | You put and get whole objects by key; you don't edit bytes in place, and "folders" are just key prefixes. That trade buys near-unlimited scale, very high durability and low cost.            | File storage                  |
| storage-redundancy-levels  | Storage redundancy (local, zone, geo)     | 1    | any      | How many copies of stored data are kept and where: several in one datacenter, spread across availability zones, or also copied to a second region.               | Each wider scope survives a bigger failure (disk, then datacenter, then region) and costs more. Geo copies are usually asynchronous, so the newest writes can be lost in a regional failover. | Backups                       |
| durability-vs-availability | Durability vs availability                | 2    | any      | Durability is the probability that stored data is never lost (for example "eleven nines"); availability is the share of time you can actually read or write it.  | Data can be perfectly safe and still unreachable during an outage. The two numbers measure different failures and are bought in different ways.                                               | Each other; SLA uptime        |
| erasure-coding             | Erasure coding                            | 3    | any      | Splitting data into k data fragments plus m parity fragments spread across disks or nodes, so that any k fragments can rebuild the original.                     | It gives the durability of many full copies for a fraction of the space (about 1.5x instead of 3x), paying with CPU and network traffic when fragments are rebuilt.                           | Replication; RAID             |
| storage-access-tiers       | Storage access tiers (hot, cool, archive) | 1    | any      | Price levels for the same data: hotter tiers cost more per GB stored but less per access; archive is cheapest to keep but offline, needing hours to rehydrate.   | Choose the tier by how often data is read, not how important it is. Retrieval fees and minimum-retention penalties make a cool tier more expensive for data that's read often.                | Redundancy levels; backups    |
| storage-lifecycle-policies | Lifecycle policies and expiry (TTL)       | 2    | any      | Rules that move data to cooler tiers or delete it after a given age or time since last access. Databases have the per-item equivalent, time to live (TTL).       | Data housekeeping on autopilot: "cool after 30 days, archive after 180, delete after 7 years" keeps cost and retention rules in line without anyone remembering.                              | Retention locks (WORM)        |
| soft-delete-and-versioning | Soft delete and object versioning         | 2    | any      | Versioning keeps every earlier version when an object is overwritten; soft delete keeps deleted data recoverable for a set period before it's purged.            | Deletes and overwrites become reversible for a while, protecting against mistakes and bad scripts, but every kept version is billed storage.                                                  | Backups; snapshots            |
| immutable-storage-worm     | Immutable storage (WORM, legal hold)      | 2    | any      | Write-once-read-many policies: time-based retention locks or legal holds under which data can't be changed or deleted, even by administrators.                   | Immutability is the protection that ransomware and rogue admins can't undo, and it's what regulators mean by tamper-proof records.                                                            | Soft delete; read-only access |

### 2. Data shapes, modelling and tenancy

| id                                | Concept                                        | Tier | Platform | What it is                                                                                                                                                                                  | The idea to get across                                                                                                                                                                                                  | Often confused with   |
| --------------------------------- | ---------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| structured-semi-unstructured-data | Structured, semi-structured, unstructured data | 1    | any      | Data with a fixed schema (rows and columns), with a flexible self-describing structure (JSON, XML), or with no inherent structure (images, video, free text).                               | The shape of the data decides where it can live and how it can be queried: tables for structured, documents for semi-structured, object storage plus extraction for unstructured.                                       | Relational vs NoSQL   |
| relational-model                  | Relational model (tables, keys, joins)         | 1    | any      | Data held as tables of rows; a primary key identifies each row, foreign keys point to rows in other tables, and joins combine tables at query time. SQL declares what you want, not how.    | Each fact is stored once and linked by keys, so the database can enforce integrity and answer questions nobody planned for by joining tables.                                                                           | Spreadsheets          |
| normalization-vs-denormalization  | Normalization vs denormalization               | 1    | any      | Normalization splits data so each fact lives in exactly one place; denormalization deliberately duplicates data so reads need fewer joins.                                                  | Normalize to make writes safe and consistent; denormalize to make reads fast, and accept that every duplicate must be kept in step.                                                                                     | Compression           |
| schema-on-write-vs-read           | Schema-on-write vs schema-on-read              | 2    | any      | Schema-on-write checks data against a declared schema when it's stored (relational tables); schema-on-read stores it as-is and applies structure when it's queried (documents, data lakes). | "Schemaless" doesn't mean no schema: the schema moves into the code that reads the data, which shifts the cost of change from migrations to every reader.                                                               | "NoSQL has no schema" |
| access-pattern-data-modelling     | Access-pattern-driven modelling (NoSQL)        | 2    | any      | Designing keys, item shapes and duplication around the exact queries the application will run, instead of normalizing entities first.                                                       | In key-value and document stores you design for the questions first: data that's read together is stored together under one key, because there are no cheap joins later.                                                | Normalization         |
| materialized-views                | Views vs materialized views                    | 2    | any      | A view is a saved query that runs again on every read; a materialized view stores the precomputed result and refreshes it when the source data changes.                                     | Materializing trades freshness and storage for read speed: the expensive join or aggregation is done once, ahead of time, not on every request.                                                                         | Cache; plain view     |
| multi-tenant-data-isolation       | Multi-tenant data isolation models             | 2    | any      | Ways to hold many customers' data: shared tables with a tenant ID column, a schema per tenant, a database per tenant, or tenants spread across shards.                                      | Isolation, cost and operational effort trade against each other: shared tables are cheapest, but one missing tenant filter or one heavy tenant affects everyone; a database each is safest and hardest to run at scale. | Sharding              |

### 3. Database families

| id                     | Concept                           | Tier | Platform | What it is                                                                                                                                                                                           | The idea to get across                                                                                                                                                                                            | Often confused with                  |
| ---------------------- | --------------------------------- | ---- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| relational-vs-nosql    | Relational vs NoSQL               | 1    | any      | The choice between relational databases (fixed schema, joins, multi-row ACID transactions) and the NoSQL families (key-value, document, wide-column, graph) built for flexible schema and scale-out. | NoSQL isn't automatically "more scalable" or "less consistent": each family gives up query flexibility to serve one access pattern well, and most systems use several stores side by side (polyglot persistence). | "NoSQL means no SQL or no schema"    |
| key-value-store        | Key-value store                   | 1    | any      | Stores an opaque value under a unique key with get, put and delete; often held in memory.                                                                                                            | Lookup by exact key is as fast and scalable as storage gets, but you can't ask anything the key doesn't answer.                                                                                                   | Cache                                |
| document-database      | Document database                 | 1    | any      | Stores self-contained JSON-like documents with nested fields and arrays, indexable and queryable by any field.                                                                                       | One document holds a whole aggregate (an order with its lines), so a single read returns everything; relationships between documents are where it gets hard.                                                      | Relational row; key-value store      |
| wide-column-store      | Wide-column (column-family) store | 2    | any      | Rows identified by a partition key plus clustering keys, each with a sparse, dynamic set of columns, spread across many nodes (Cassandra, HBase, Bigtable).                                          | Data is kept sorted by key within each partition, so you design the key to make each query one contiguous read; it's built for huge write volumes.                                                                | Columnar (analytical) storage        |
| graph-database         | Graph database                    | 2    | any      | Stores nodes and edges, both with properties, and queries by traversing relationships (Cypher, Gremlin).                                                                                             | When the question is about connections (friends of friends, fraud rings, dependencies), following edges beats piling up joins that grow with every hop.                                                           | Relational tables with foreign keys  |
| time-series-database   | Time-series database              | 2    | any      | Optimized for append-only timestamped measurements with tags, with time-window queries, downsampling and retention built in.                                                                         | Data arrives in time order and is read by time range, so the engine can compress heavily and drop old data cheaply; the number of distinct tag combinations is what hurts.                                        | Log store                            |
| search-engine-database | Search engine (inverted index)    | 2    | any      | Indexes text into an inverted index (each term points to the documents containing it) for full-text, fuzzy and relevance-ranked search with filters and facets.                                      | Search turns the data inside out: instead of scanning documents for a word, it looks the word up. The index is a derived, eventually consistent copy, not the system of record.                                   | A LIKE query in a database           |
| vector-database        | Vector database                   | 2    | any      | Stores embeddings (long lists of numbers that encode meaning) and returns those nearest to a query vector, usually through approximate nearest-neighbour indexes.                                    | It retrieves by similarity of meaning rather than exact match; approximate indexes give up a little accuracy for a very large gain in speed.                                                                      | Search engine                        |
| distributed-sql        | Distributed SQL (NewSQL)          | 3    | any      | Relational databases that shard and replicate automatically across nodes or regions while keeping SQL and serializable transactions (Spanner, CockroachDB, YugabyteDB).                              | They get NoSQL-style scale-out with relational guarantees by running consensus per shard and coordinating transactions across shards, paying for it in write latency.                                             | Manually sharded relational database |

### 4. Transactions and concurrency

| id                                | Concept                               | Tier | Platform | What it is                                                                                                                                                                                   | The idea to get across                                                                                                                                                                                | Often confused with        |
| --------------------------------- | ------------------------------------- | ---- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| acid-transactions                 | ACID transactions                     | 1    | any      | A transaction groups several reads and writes into one unit that is Atomic, Consistent, Isolated and Durable.                                                                                | All or nothing: if anything fails part-way, every change is rolled back, so nobody ever sees half a money transfer.                                                                                   | The "C" in CAP             |
| isolation-levels                  | Isolation levels                      | 2    | any      | Read uncommitted, read committed, repeatable read (snapshot) and serializable: settings for how much concurrent transactions can see of each other's work.                                   | Weaker levels are faster but allow specific anomalies. The same name means different things in different databases: PostgreSQL's repeatable read is snapshot isolation, SQL Server's uses held locks. | Consistency models         |
| dirty-read                        | Dirty read                            | 2    | any      | A transaction reads data that another transaction has written but not yet committed.                                                                                                         | If the writer rolls back, the reader acted on data that never existed. Read committed and anything stronger prevent it.                                                                               | Non-repeatable read        |
| non-repeatable-read               | Non-repeatable read (read skew)       | 2    | any      | Reading the same row twice in one transaction returns different values because another transaction committed in between.                                                                     | Under read committed each statement sees the latest committed data, so a report or backup can mix before and after states of the same data.                                                           | Phantom read               |
| phantom-read                      | Phantom read                          | 2    | any      | Re-running the same range or filter query in one transaction returns extra or missing rows because another transaction inserted or deleted matching rows.                                    | Locking the rows you've read isn't enough; protection must cover rows that don't exist yet (range or predicate locks, or a snapshot).                                                                 | Non-repeatable read        |
| lost-update                       | Lost update                           | 2    | any      | Two transactions read the same value, each changes it and writes it back; the second write silently overwrites the first.                                                                    | Read-modify-write cycles need protection: an atomic update (`SET x = x + 1`), an explicit lock (`SELECT ... FOR UPDATE`) or a compare-and-set.                                                        | Dirty write                |
| write-skew                        | Write skew                            | 3    | any      | Two transactions read overlapping data, each decides based on what it read, and they write different rows, together breaking a rule neither broke alone (both on-call doctors go off call).  | Snapshot isolation can't catch it because the two never touch the same row; only serializable isolation, or explicitly locking what the decision was based on, prevents it.                           | Lost update                |
| mvcc                              | MVCC and snapshot isolation           | 2    | any      | Multi-version concurrency control keeps several versions of each row, so each transaction reads a consistent snapshot from when it started; old versions are cleaned up later (vacuum).      | Readers never block writers and writers never block readers, because each transaction reads the versions that were current for it.                                                                    | Optimistic locking         |
| serializability                   | Serializability                       | 3    | any      | The strongest isolation: the outcome is as if transactions ran one at a time. Achieved by actually running them serially, by two-phase locking, or by serializable snapshot isolation (SSI). | Serializable removes every race condition, at the cost of transactions blocking or being aborted, so the application must be ready to retry.                                                          | Linearizability            |
| optimistic-vs-pessimistic-locking | Optimistic vs pessimistic concurrency | 2    | any      | Pessimistic: lock data before changing it, so others wait. Optimistic: let everyone proceed and check a version number or ETag at write time, rejecting whoever is second.                   | Lock first when conflicts are common, check at write time when they're rare. With optimistic concurrency a conflict means a retry, not a wait.                                                        | MVCC                       |
| database-deadlock                 | Deadlock                              | 2    | any      | Two or more transactions each hold a lock another one needs, so none can continue; the database spots the cycle and aborts one of them.                                                      | Deadlocks come from taking locks in different orders. A consistent lock order and short transactions prevent them, and the aborted transaction must retry.                                            | Lock contention (blocking) |
| two-phase-commit                  | Two-phase commit (2PC)                | 3    | any      | A coordinator asks every participant to prepare (promise it can commit), then tells all of them to commit or abort, making one transaction atomic across databases or shards.                | It gives atomicity across machines, but if the coordinator dies after "prepare", participants are stuck holding locks until it comes back.                                                            | Two-phase locking; sagas   |

### 5. Replication and failover

| id                          | Concept                                 | Tier | Platform | What it is                                                                                                                                                                                               | The idea to get across                                                                                                                                                                                      | Often confused with            |
| --------------------------- | --------------------------------------- | ---- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| leader-follower-replication | Leader-follower replication             | 1    | any      | One node (leader, primary) accepts writes and streams its change log to followers (replicas), which apply the changes in the same order.                                                                 | A single writer means no write conflicts; the copies give redundancy and read capacity, at the price of followers trailing behind.                                                                          | Backups; sharding              |
| sync-vs-async-replication   | Synchronous vs asynchronous replication | 2    | any      | Synchronous replication waits for a replica to confirm before acknowledging a write; asynchronous acknowledges at once and ships the change afterwards.                                                  | Sync guarantees a replica has every acknowledged write but adds latency and can stall writes; async is fast, but a failover can lose the last few seconds of writes.                                        | Strong vs eventual consistency |
| replication-lag             | Replication lag                         | 2    | any      | The delay between a write on the leader and its appearance on a follower: milliseconds normally, minutes under load.                                                                                     | Lag shows up as user-visible bugs: your own write disappears, data appears then vanishes as you hit different replicas (non-monotonic reads), or an answer shows before its question (inconsistent prefix). | Network latency                |
| read-replicas               | Read replicas                           | 1    | any      | Follower copies that serve read-only queries to take load off the primary.                                                                                                                               | They scale reads, not writes, and every read from them may be slightly stale.                                                                                                                               | Standby replica; sharding      |
| multi-leader-replication    | Multi-leader replication                | 3    | any      | More than one node accepts writes (often one per region, or each offline device) and they replicate to each other asynchronously.                                                                        | Writes are fast and local everywhere, but the same record can change in two places at once, so a conflict-resolution strategy is mandatory.                                                                 | Leaderless replication         |
| leaderless-replication      | Leaderless replication                  | 3    | any      | Clients write to and read from several replicas directly, with no leader (Dynamo-style); stale replicas are fixed by read repair and background anti-entropy.                                            | No failover is needed because no node is special; consistency comes from overlapping read and write sets plus repair, not from one source of truth.                                                         | Multi-leader replication       |
| quorum-reads-writes         | Quorum reads and writes                 | 2    | any      | With N replicas, a write needs W acknowledgements and a read asks R replicas; when W + R > N, every read overlaps at least one replica holding the latest write.                                         | Tuning W and R trades latency and availability against freshness. The overlap is the whole trick, and edge cases (sloppy quorums, concurrent writes) can still return stale data.                           | Consensus; majority voting     |
| write-conflict-resolution   | Write conflict resolution (LWW, CRDTs)  | 3    | any      | Ways to reconcile concurrent writes to the same data: last-write-wins by timestamp, version vectors or logical clocks to detect concurrency, application-level merge, or CRDTs that merge automatically. | Last-write-wins is simple but silently throws writes away and trusts clocks that drift; detecting the conflict and merging, or using CRDTs, keeps everyone's changes.                                       | Lost update                    |
| database-failover           | Database failover                       | 2    | any      | When the primary fails, a replica is promoted to primary and clients are redirected to it, automatically or by an operator.                                                                              | Failover is a trade: detecting failure relies on timeouts (too short causes needless failovers, too long means downtime), and with async replication the new primary may be missing acknowledged writes.    | Restoring from backup          |
| split-brain                 | Split brain and fencing                 | 2    | any      | Two nodes both believe they're the leader, usually after a network partition, and both accept writes. Fencing tokens or majority-based leases stop the old leader.                                       | A node can't tell "the others are dead" from "I'm cut off", so safe systems need a majority vote and a way to fence out the stale leader.                                                                   | Failover                       |
| consensus-raft-paxos        | Consensus (Raft, Paxos)                 | 3    | any      | Algorithms that let a group of nodes agree on a value or an ordered log despite failures, as long as a majority is up; used for leader election and replicated configuration (etcd, ZooKeeper).          | Majorities always overlap, so two leaders can never both commit: 2f+1 nodes tolerate f failures and keep a single agreed history.                                                                           | Quorum reads/writes; 2PC       |
| geo-replication             | Geo-replication                         | 2    | any      | Replicating a database or storage account to another region, usually asynchronously, for disaster recovery and reads close to users.                                                                     | It protects against losing a region and puts data near users, but distance forces a choice: slow writes (sync) or possible data loss on failover (async).                                                   | Zone redundancy; backups       |

### 6. Consistency models and trade-offs

| id                             | Concept                               | Tier | Platform | What it is                                                                                                                                                                         | The idea to get across                                                                                                                                                         | Often confused with             |
| ------------------------------ | ------------------------------------- | ---- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------- |
| cap-theorem                    | CAP theorem                           | 1    | any      | During a network partition, a replicated data store must choose between consistency (every read sees the latest write) and availability (every request gets a non-error answer).   | Partitions aren't optional, so the real choice is what to do when one happens: refuse some requests or serve possibly stale data. CAP says nothing about normal operation.     | ACID consistency; "pick 2 of 3" |
| pacelc                         | PACELC                                | 3    | any      | Extends CAP: if Partitioned, choose Availability or Consistency; Else, in normal operation, choose Latency or Consistency.                                                         | Even with nothing broken, stronger consistency costs latency because replicas must coordinate, and that's the trade-off you pay on every request.                              | CAP theorem                     |
| strong-vs-eventual-consistency | Strong vs eventual consistency        | 1    | any      | Strong: once a write is acknowledged, every reader sees it. Eventual: replicas converge once writes stop, but reads may be stale in the meantime.                                  | "Eventually" has no deadline. Eventual consistency is fine for like counts and dangerous for account balances.                                                                 | Weak isolation levels           |
| linearizability                | Linearizability                       | 3    | any      | Every operation appears to take effect at a single instant between its start and its end, as if there were only one copy of the data.                                              | Once any client has seen a new value, nobody can see the old one again; this is what makes locks, leader election and uniqueness checks safe.                                  | Serializability                 |
| sequential-consistency         | Sequential consistency                | 3    | any      | All clients see all operations in one agreed order that respects each client's own order, but that order needn't match real time.                                                  | Everyone agrees on the story, but the story can run behind the clock: weaker than linearizable, stronger than causal.                                                          | Linearizability                 |
| causal-consistency             | Causal consistency                    | 3    | any      | Operations that are causally related (a reply and the message it answers) are seen in that order by everyone; unrelated operations may appear in any order.                        | It's the strongest model that can stay available during a partition (with clients sticking to a replica), and it prevents the "answer before question" anomalies users notice. | Eventual consistency            |
| read-your-writes               | Read-your-writes (session guarantees) | 2    | any      | A client always sees its own earlier writes, even when reading from replicas. Related session guarantees: monotonic reads (time never goes backwards) and consistent prefix reads. | Users rarely need global freshness, they need to see their own actions; per-session guarantees fix the visible bugs cheaply.                                                   | Strong consistency              |
| bounded-staleness              | Bounded staleness                     | 3    | any      | Reads may lag behind writes, but by no more than a fixed number of versions or amount of time.                                                                                     | It turns "eventually" into a number you can reason about and promise to customers.                                                                                             | Eventual consistency            |

### Vendor isolation-level documentation

| Source                 | What it shows                                                                                                                            | Catalog                                                                     |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| PostgreSQL             | Read uncommitted behaves as read committed; repeatable read is snapshot isolation (no phantoms); serializable is SSI; write-skew example | `isolation-levels`, `mvcc`, `serializability`, `write-skew`                 |
| SQL Server / Azure SQL | Read committed uses locks unless READ_COMMITTED_SNAPSHOT is on (default on Azure SQL); SNAPSHOT level; serializable uses range locks     | `isolation-levels`, `mvcc`, `phantom-read`; RCSI default is an Azure detail |
| MySQL InnoDB           | Repeatable read is the default; consistent snapshot reads; next-key (gap) locks prevent phantoms                                         | `isolation-levels`, `phantom-read`, `optimistic-vs-pessimistic-locking`     |
| Hermitage              | Same level names give different guarantees across databases; anomalies G0 to G2 including lost update and read skew                      | `isolation-levels`, `lost-update`, `non-repeatable-read`, `write-skew`      |
