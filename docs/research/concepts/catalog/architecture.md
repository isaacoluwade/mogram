# Architecture patterns: concept catalog

Stage 1 research for the **Architecture** area (see [the brief](../README.md)). This file lists every
major concept in the area and nothing about how to draw them.

## Scope

**In:** how systems are shaped and divided.

- **Architecture styles:** client-server, monolith, modular monolith, layered/n-tier,
  microservices, SOA, serverless application design, web-queue-worker, pipes and filters, plus
  the specialist styles (microkernel, space-based, peer-to-peer, big compute).
- **Decomposition and boundaries:**
  - coupling and cohesion;
  - DDD strategic design: bounded contexts, subdomains, context maps, aggregates;
  - Conway's law;
  - the anti-patterns: distributed monolith, big ball of mud.
- **Data ownership across services:** database per service vs shared database, API
  composition, CQRS, event sourcing, valet key.
- **Integration and the edge:**
  - the API gateway and its three gateway patterns;
  - backends for frontends, gatekeeper;
  - API styles and versioning;
  - synchronous call chains;
  - service discovery, service mesh, the sidecar family;
  - micro frontends.
- **Migration and modernization patterns:** strangler fig, branch by abstraction, splitting
  the database.
- **Code structure inside a service** (tier 3): hexagonal, clean/onion.
- **Cloud-native and operational principles:** twelve-factor, cattle vs pets, fallacies of
  distributed computing, external configuration, quarantine.
- **Multi-tenancy and deployment topologies:** tenancy models, deployment stamps, geodes,
  compute consolidation.
- **Architecture decisions:** trade-offs, architecture characteristics, ADRs, the C4 model,
  fitness functions, when microservices pay off.

**Left to other areas.** Each of these is listed under [Overlaps](#overlaps) with its owning id.

### Architecture styles

| id                            | Concept                             | Tier | Platform | What it is                                                                                                                                                                               | The idea to get across                                                                                                                                                                                                                                                                          | Often confused with                                                                                              |
| ----------------------------- | ----------------------------------- | ---- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| client-server                 | Client-server                       | 1    | any      | Clients send requests to a server that owns the data and logic, and the server sends back responses.                                                                                     | The server is the shared central authority that many clients come and go from. Almost every other style (web apps, APIs, n-tier) refines this request/response split.                                                                                                                           | Peer-to-peer (no central server)                                                                                 |
| monolithic-architecture       | Monolith                            | 1    | any      | One deployable unit that contains all of an application's features, usually running as one process against one database.                                                                 | Everything ships and scales together. It's simple to build, test and call (in-process function calls), but one change redeploys everything and one hot path forces you to scale the whole thing. "Monolith" describes how it's deployed, not how good it is.                                    | Big ball of mud (a monolith can be well structured)                                                              |
| modular-monolith              | Modular monolith                    | 2    | any      | One deployable application divided internally into strongly bounded modules, each owning its own data and reached only through explicit interfaces.                                      | You get most of the boundary benefits of microservices (ownership, clear contracts) without network calls. Modules can later be pulled out as services along seams you've already drawn.                                                                                                        | Microservices; a layered monolith (layers are horizontal, modules are vertical slices of the business)           |
| n-tier-architecture           | Layered / N-tier architecture       | 1    | any      | An application split into horizontal layers (presentation, business logic, data access) that may run on separate physical tiers, with each layer calling only the one below it.          | Layers are the logical separation and tiers are the physical deployment. The classic three-tier web app (web, app, database) isolates technical concerns, but a single feature change usually cuts through every layer.                                                                         | Microservices (vertical split by business capability vs horizontal split by technical concern)                   |
| microservices-architecture    | Microservices                       | 1    | any      | An application built as a set of small, independently deployable services, each owning one business capability and its own data, communicating over the network.                         | Independence is the point: each team can change, deploy and scale its service on its own. The price is distributed-systems complexity: network failures, data consistency across services, and harder observability.                                                                            | SOA; "small services" that share a database or must deploy together (a distributed monolith)                     |
| service-oriented-architecture | Service-oriented architecture (SOA) | 2    | any      | An enterprise style where shared, reusable services are integrated through a central enterprise service bus that handles routing, transformation and orchestration.                      | SOA put the intelligence in the middleware ("smart pipes"). Microservices moved it back into the services ("smart endpoints, dumb pipes"), giving up enterprise-wide reuse for team-level independence.                                                                                         | Microservices                                                                                                    |
| serverless-architecture       | Serverless application architecture | 1    | any      | Designing an application as small, event-triggered functions glued together by managed services (API gateway, queues, storage, databases), with no long-running server code of your own. | The design moves from servers to events. Each function is small, stateless and started by something happening, and all state lives in managed services. You trade control for zero idle cost and automatic scale, and accept execution limits, cold starts and deeper coupling to one provider. | Serverless computing as a service and billing model (Fundamentals); containers as a service (still long-running) |

### Specialist styles and processing patterns

| id                         | Concept                            | Tier | Platform | What it is                                                                                                                                                                                    | The idea to get across                                                                                                                                                                                                                            | Often confused with                                                                                                         |
| -------------------------- | ---------------------------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| web-queue-worker           | Web-Queue-Worker                   | 2    | any      | A web front end handles requests and puts slow or heavy work on a queue for background workers to process asynchronously.                                                                     | Keep the user-facing tier fast by never doing slow work inside a request. The front end and workers scale independently, and the queue absorbs bursts between them.                                                                               | Microservices (just two roles, often sharing a database); queue-based load leveling (the queue's role, not the whole style) |
| pipes-and-filters          | Pipes and Filters                  | 2    | any      | A processing task split into a chain of independent steps (filters) joined by channels (pipes). Each filter transforms the data and passes it on.                                             | Each filter does one job and can be reused, reordered, scaled or replaced on its own. The slowest filter sets the throughput, so that's the one you scale.                                                                                        | Data ETL pipelines; CI/CD pipelines                                                                                         |
| scheduler-agent-supervisor | Scheduler Agent Supervisor         | 3    | any      | A scheduler drives the steps of a distributed workflow, agents wrap the calls to each remote service, and a supervisor watches the recorded state to retry or roll back stuck steps.          | Make multi-step distributed work recoverable. Durable state for every step, plus a watchdog that spots timeouts and either retries or compensates, replaces hoping that every remote call succeeds.                                               | Saga orchestration and durable execution engines (Messaging: modern implementations of the same idea)                       |
| microkernel-architecture   | Microkernel (plug-in) architecture | 3    | any      | A minimal core system that provides the essential functions and a plug-in registry, extended by independent plug-in modules.                                                                  | What varies lives in plug-ins, so you can add features or customer-specific rules without changing the core. IDEs, browsers and rules engines are built this way.                                                                                 | Modular monolith; microservices                                                                                             |
| space-based-architecture   | Space-based architecture           | 3    | any      | Processing units each hold application logic plus a replica of an in-memory data grid. Virtualized middleware coordinates them, and the database is updated asynchronously in the background. | Take the central database out of the request path to survive extreme, spiky concurrency. Requests hit replicated in-memory data, and data pumps persist the changes later.                                                                        | Caching (here the in-memory grid is the primary store for transactions)                                                     |
| peer-to-peer               | Peer-to-peer                       | 3    | any      | Every node is both client and server, sharing resources directly with other peers without a central authority.                                                                                | There's no single server to overload or take down, and capacity grows with the number of peers. Discovery, trust and consistency all get harder.                                                                                                  | Client-server; mesh networking                                                                                              |
| big-compute                | Big compute (HPC)                  | 3    | any      | Very large computational jobs split into many tasks that a scheduler runs in parallel across hundreds or thousands of cores.                                                                  | Embarrassingly parallel tasks scale almost linearly as you add cores. Tightly coupled tasks need low-latency interconnects (RDMA, InfiniBand) because the nodes talk constantly. The cloud lets you burst to thousands of cores just for the job. | Big data (bound by data volume, not compute); autoscaling web apps                                                          |

### Decomposition and boundaries

| id                                 | Concept                                                     | Tier | Platform | What it is                                                                                                                                                                                                | The idea to get across                                                                                                                                                                                                                                                     | Often confused with                                                                                               |
| ---------------------------------- | ----------------------------------------------------------- | ---- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| coupling-and-cohesion              | Coupling and cohesion                                       | 1    | any      | Coupling is how much one component depends on another. Cohesion is how closely related the responsibilities inside one component are.                                                                     | Good boundaries keep things that change together in one place (high cohesion) and keep the connections between places few and stable (loose coupling). Nearly every pattern in this area moves a boundary toward that.                                                     | Dependency in general (coupling is its degree and kind: temporal, deployment, data, domain)                       |
| service-decomposition              | Service decomposition (by business capability or subdomain) | 2    | any      | Splitting a system into services along what the business does (orders, payments, shipping) rather than along technical layers (UI, logic, database).                                                      | Split vertically by business capability so a typical change lands in one service. Splitting horizontally by technology guarantees that every feature touches every service.                                                                                                | N-tier layering; one service per entity or table                                                                  |
| service-granularity                | Service granularity                                         | 3    | any      | Deciding how big each service should be, anywhere from a few coarse domain services to many fine-grained nano-services.                                                                                   | Smaller isn't automatically better. Independent scaling, fault isolation and team ownership push services apart. Shared transactions, chatty workflows and shared data pull them back together.                                                                            | Lines of code as a measure of size; the "micro" in microservices                                                  |
| domain-driven-design               | Domain-driven design (DDD)                                  | 2    | any      | A design approach that models the business domain closely with domain experts, in their language, and splits large domains into explicitly bounded models.                                                | Software structure should mirror the business. DDD's strategic half (bounded contexts, context maps) is what actually draws service boundaries.                                                                                                                            | Data modelling; microservices (DDD predates them and applies to monoliths too)                                    |
| bounded-context                    | Bounded context                                             | 2    | any      | An explicit boundary inside which one domain model and its ubiquitous language are consistent.                                                                                                            | The same word legitimately means different things in different parts of a business: "customer" in sales, support and billing. Give each meaning its own model and boundary rather than one shared model that suits nobody.                                                 | A microservice (contexts and services don't always map one-to-one); a subdomain (problem space vs solution space) |
| core-supporting-generic-subdomains | Core, supporting and generic subdomains                     | 3    | any      | Classifying the parts of a business domain as core (what differentiates you), supporting (needed and specific to you) or generic (solved problems such as payments or identity).                          | Spend your best design effort on the core. Buy or adopt generic subdomains instead of building them.                                                                                                                                                                       | Bounded contexts (subdomains are the problem, contexts are your model of it)                                      |
| ddd-aggregate                      | Aggregate                                                   | 2    | any      | A cluster of domain objects that change as one unit, with a single root entity that enforces their rules (invariants).                                                                                    | The aggregate is the consistency and transaction boundary. Change one aggregate per transaction, refer to others by ID, and accept eventual consistency between aggregates, usually through domain events. That's why aggregates map cleanly onto services and partitions. | Database tables; ORM object graphs                                                                                |
| context-map                        | Context map                                                 | 3    | any      | A map of the bounded contexts and the relationships between them: partnership, shared kernel, customer/supplier, conformist, anti-corruption layer, open host service, published language, separate ways. | How teams and models integrate is a design decision with power dynamics. The map makes upstream and downstream dependencies, and the places where translation happens, visible.                                                                                            | A deployment diagram (a context map shows model and team relationships, not infrastructure)                       |
| anti-corruption-layer              | Anti-corruption layer                                       | 2    | any      | A translation layer between your system and a legacy or external system whose model is different, converting requests and data in both directions.                                                        | Keep a foreign or legacy model from leaking into your clean one. All translation lives in one disposable place, which also makes the layer a key migration tool.                                                                                                           | Adapter or facade (the same idea at code scale); API gateway                                                      |
| event-storming                     | Event storming                                              | 3    | any      | A collaborative workshop where domain experts and engineers lay out a business process as a timeline of domain events on sticky notes, then add commands, actors, policies and aggregates.                | Boundaries emerge from the flow of events. Where the language or ownership changes along the timeline is where bounded contexts, and services, split.                                                                                                                      | UML or process modelling done by engineers alone                                                                  |
| conways-law                        | Conway's law                                                | 2    | any      | Organizations design systems that mirror their own communication structure.                                                                                                                               | Team boundaries become system boundaries whether you plan it or not. The "inverse Conway maneuver" deliberately shapes teams to get the architecture you want.                                                                                                             | A technical rule (it's a sociotechnical observation)                                                              |
| distributed-monolith               | Distributed monolith                                        | 2    | any      | A system split into separate services that are still so tightly coupled they must be changed, deployed or scaled together.                                                                                | Shared databases, long synchronous chains or lockstep releases give you all of the costs of microservices and none of the independence: the worst of both worlds.                                                                                                          | Microservices; modular monolith                                                                                   |
| big-ball-of-mud                    | Big ball of mud                                             | 3    | any      | A system with no discernible structure, where everything depends on everything.                                                                                                                           | Architecture decays without deliberate boundaries. The DDD response is to fence the mud off behind a boundary so it stops spreading, not to redesign it all at once.                                                                                                       | Monolith                                                                                                          |

### Data across services

| id                   | Concept                                         | Tier | Platform | What it is                                                                                                                                            | The idea to get across                                                                                                                                                                                                 | Often confused with                                                                                            |
| -------------------- | ----------------------------------------------- | ---- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| database-per-service | Database per service                            | 2    | any      | Each service owns its data privately. Other services reach it only through that service's API or events.                                              | Private data is what makes services independently changeable. The consequence is no cross-service joins and no ACID transactions across services, so you need API composition, CQRS views and sagas instead.           | A separate database server per service (the boundary is ownership; services can share a server but not tables) |
| shared-database      | Shared database (integration database)          | 2    | any      | Several services read and write the same database tables.                                                                                             | It's simple and keeps ACID transactions, but the schema becomes a hidden contract. One team's change can break the others, and no service can be deployed independently.                                               | Database per service with several databases on one physical server                                             |
| api-composition      | API composition                                 | 2    | any      | A composer (often a gateway or a service) answers a query by calling each service that owns part of the data and joining the results in memory.       | You get cross-service reads without shared tables, at the cost of extra calls, in-memory joins, and an answer that's only available when every service involved is up.                                                 | Gateway aggregation (API composition done at the edge); a CQRS read model                                      |
| cqrs                 | CQRS (Command Query Responsibility Segregation) | 2    | any      | Separate models, and often separate stores, for writing data and for reading it.                                                                      | Reads and writes have different shapes and loads, so optimize each one independently. The catch is that read models lag behind writes (eventual consistency).                                                          | Event sourcing (often paired with it, but independent); read replicas (the same model, copied)                 |
| event-sourcing       | Event sourcing                                  | 3    | any      | Storing the full, append-only sequence of state-changing events as the source of truth, and deriving current state by replaying them.                 | You keep the full history and the "why", can rebuild state or build new views as of any point in time, and get events to publish for free. The costs are replay, snapshots, event schema evolution and harder queries. | Event-driven architecture; audit logging; change data capture                                                  |
| valet-key            | Valet key                                       | 2    | any      | The application gives a client a scoped, time-limited token (such as a SAS token or presigned URL) to read or write one resource in storage directly. | Take your servers out of the data path. The app authorizes, the storage service does the heavy transfer, and the token limits what can be done and for how long.                                                       | Gatekeeper; API keys (long-lived and broad)                                                                    |

### Integration and edge

| id                        | Concept                          | Tier | Platform | What it is                                                                                                                                                                                                     | The idea to get across                                                                                                                                                                                                                                             | Often confused with                                                                                                                  |
| ------------------------- | -------------------------------- | ---- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| api-gateway               | API gateway                      | 1    | any      | A single entry point in front of a set of backend services that routes requests and handles cross-cutting concerns such as authentication, rate limiting and TLS.                                              | Clients see one stable API, while the services behind it stay free to split, move and change. A gateway combines routing, aggregation and offloading, but it becomes a bottleneck or a new monolith if business logic creeps in.                                   | Load balancer or reverse proxy (routes by host or path without API concerns); service mesh (traffic between services)                |
| gateway-routing           | Gateway routing                  | 2    | any      | A gateway that maps one public endpoint to many backend services using the request's path, host name or headers.                                                                                               | Clients only need one address. You can move, split, version or canary services by changing routes instead of clients.                                                                                                                                              | Load balancing (spreading load across identical instances vs choosing between different services)                                    |
| gateway-aggregation       | Gateway aggregation              | 2    | any      | A gateway that fans one client request out to several backend services and returns a single combined response.                                                                                                 | Cut chattiness for distant clients such as mobile apps on high-latency networks: one round trip over the internet, several fast ones inside the data centre.                                                                                                       | API composition; backends for frontends                                                                                              |
| gateway-offloading        | Gateway offloading               | 2    | any      | Moving shared cross-cutting work out of every service and into the gateway: TLS termination, authentication, rate limiting, caching, compression.                                                              | Implement it once at the edge instead of in every service and every language. Services get simpler and policy stays consistent.                                                                                                                                    | Sidecar (offloads per instance rather than at the edge)                                                                              |
| backends-for-frontends    | Backends for frontends (BFF)     | 2    | any      | A separate backend or gateway for each kind of client (web, mobile, partner), shaped to that client's needs and usually owned by the client's team.                                                            | One general-purpose API serves every client badly. A BFF per experience gives each client exactly the data and shape it needs without coordinating with the others.                                                                                                | API gateway (one shared gateway for all clients)                                                                                     |
| gatekeeper-pattern        | Gatekeeper                       | 3    | any      | A dedicated, hardened host that validates and sanitizes every request and forwards only safe ones to trusted back ends, which hold the keys and the data.                                                      | Separate exposure from privilege. The internet-facing host has no secrets, so compromising it doesn't give an attacker access to storage or data.                                                                                                                  | Gateway offloading; web application firewall                                                                                         |
| api-styles                | API styles: REST, gRPC, GraphQL  | 2    | any      | The main ways services expose interfaces: resource-oriented HTTP (REST), contract-first binary RPC (gRPC), and client-specified queries over a typed schema (GraphQL).                                         | Choose by consumer. REST is universal and cache-friendly. gRPC is fast and strongly typed for service-to-service calls. GraphQL lets varied clients fetch exactly what they need in one request.                                                                   | Transport protocols (HTTP/2 is a transport that gRPC uses, not an API style)                                                         |
| api-versioning            | API versioning and compatibility | 2    | any      | Changing an API without breaking existing consumers: additive changes, tolerant readers, and explicit versions in the path, a header or the media type.                                                        | Independently deployed services can't upgrade all their consumers at once. Make changes backward compatible by default, and run old and new versions side by side when you can't.                                                                                  | Release version numbers (semver of the deployable); event schema evolution (Messaging: the same problem for events)                  |
| synchronous-call-chain    | Synchronous call chains          | 2    | any      | A request that has to pass through several services calling each other in sequence before the user gets an answer.                                                                                             | The caller is stuck until the slowest link answers: latencies add up, availabilities multiply down (five services at 99.9% each give about 99.5%), and one slow service stalls everything upstream. Shorten chains, go asynchronous, or keep local copies of data. | Composite availability (Reliability: the arithmetic alone); retries in a service mesh (they hide the coupling, they don't remove it) |
| service-discovery         | Service discovery                | 2    | any      | How a service finds the current addresses of another service's instances: instances register with a registry, and either the client (client-side discovery) or a router (server-side discovery) looks them up. | Instances come and go with scaling and failures, so addresses can't be hard-coded. A registry kept current by health checks acts as the live phone book.                                                                                                           | DNS (one discovery mechanism among several); load balancer                                                                           |
| service-mesh              | Service mesh                     | 2    | any      | A layer of proxies beside every service (the data plane), configured centrally (the control plane), that handles service-to-service traffic: mTLS, retries, timeouts, traffic splitting and telemetry.         | Networking and security concerns move out of application code into the platform, consistently across every service and language. The cost is extra hops, extra resources and operational complexity.                                                               | API gateway (traffic entering at the edge vs traffic between services)                                                               |
| sidecar-pattern           | Sidecar                          | 2    | any      | A helper process or container deployed next to each application instance, sharing its host and lifecycle, that adds a capability such as logging, proxying or configuration.                                   | Add cross-cutting features without changing or recompiling the app, whatever its language. It's the out-of-process alternative to a shared library (a "microservice chassis").                                                                                     | Ambassador and adapter (specialized sidecars); a separate shared service                                                             |
