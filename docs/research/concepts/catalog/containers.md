# Containers & Kubernetes: concept catalog

Stage 1 research for the Containers area. Checked in October 2026 against the Kubernetes v1.37
documentation and the CNCF curricula listed under Sources.

## 1. Scope

**In:**

- **Containers, platform-neutral.** What a container is and how it compares to a VM, the kernel
  features underneath (namespaces, cgroups), runtimes and the OCI standards, isolation and
  sandboxing, local data and multi-container apps (Docker Compose), and why orchestration exists.
- **Images.** Images, layers, Dockerfiles, the build cache, multi-stage and multi-platform builds,
  registries, tags and digests.
- **Kubernetes, end to end:**
  - architecture and the API model (control plane, nodes, desired state, controllers)
  - workloads
  - Service networking (Services, DNS, Ingress, Gateway API, NetworkPolicy)
  - configuration and storage
  - scheduling and resource management
  - autoscaling
  - health and disruption
  - security, as far as Kubernetes implements it
  - extension points (CRI, CNI, CSI, CRDs, operators)
  - packaging (Helm, Kustomize) and service mesh
  - running clusters (managed Kubernetes, upgrades, high availability, etcd, kubeadm)
  - troubleshooting

**Left to other areas** (they're listed under Overlaps, not catalogued here):

- **Networking:** general theory such as overlays, BGP, L4 and L7 load balancing, DNS and TLS.
- **Security:** supply-chain theory (scanning, signing, SBOMs, provenance), mTLS as a general
  idea, secret managers, KMS envelope encryption, runtime threat detection and CIS benchmarks.
- **Delivery:** CI/CD, GitOps controllers (Argo CD, Flux) and release strategies as general
  ideas.
- **Observability:** metrics, traces and log back ends.
- **Data:** consensus and quorum theory.
- **Reliability:** backup and DR in general.
- **AI systems:** gang scheduling of AI jobs and model serving.
- **Azure, AWS and Google Cloud files:** AKS, EKS and GKE specifics, cloud registries and
  serverless container services.

**Excluded outright:**

- Windows containers and Windows nodes.
- Multi-cluster federation and cross-cluster service discovery.
- Other orchestrators (Nomad, Swarm). ECS belongs to the AWS file.
- Docker Desktop product features.

| container-vs-vm               | Containers vs virtual machines       | 1    | any      | A VM virtualises hardware and boots its own guest kernel on a hypervisor. A container is an ordinary process on the host. ### 3.2 Images, builds and registries

| container-image                | Container image                            | 1    | any      | A versioned package that never changes once built. It holds a filesystem (app, runtime, libraries) and metadata (entrypoint, environment, ports), stored as a manifest, a config and a stack of layers.                                                              | An image is a snapshot of everything the app needs to run. A container is a running instance of it: one image, many identical containers, on any machine.                                                                                                   | Container (the running instance); VM image                              |
| container-image-layers         | Image layers and copy-on-write             | 2    | any      | Each build step that changes the filesystem adds a read-only layer named by the hash of its contents. A union filesystem (overlayfs) stacks the layers. Each running container gets its own thin writable layer on top and copies a file up only when it changes it. | Layers are shared and cached by digest, so ten images built on the same base store it once. Layers only add, so deleting a file in a later step hides it but never shrinks the image.                                                                       | Build cache; the container's writable layer                             |
| container-dockerfile           | Dockerfile                                 | 1    | any      | A text recipe of instructions (`FROM`, `RUN`, `COPY`, `ENV`, `USER`, `EXPOSE`, `ENTRYPOINT`, `CMD`). In Kubernetes, `command` replaces `ENTRYPOINT` and `args` replaces `CMD`.            | `ENTRYPOINT` vs `CMD`; build context vs image contents                  |
| container-build-cache          | Build cache                                | 2    | any      | The builder reuses a layer when its instruction and inputs (the files copied, the previous layer) are unchanged. The first changed step rebuilds that layer and every step after it.                                                                                 | Order instructions from least to most often changing. Copy the dependency manifest and install before copying the source, and a code edit rebuilds in seconds instead of reinstalling everything.                                                           | Image layers (how images are stored) vs the cache (reuse at build time) |
| container-multi-stage-build    | Multi-stage builds and minimal base images | 2    | any      | A Dockerfile with several `FROM` stages. It compiles in a full SDK image, then uses `COPY --from` to copy only the built artifact into a small runtime base (slim, distroless or scratch).                                                                           | Build tools are needed to make the app, not to run it. Leaving them behind cuts image size, pull time and attack surface: fewer packages, fewer CVEs and often no shell.                                                                                    | Alpine images (small, but still a full distro)                          |
| container-multi-platform-image | Multi-platform images                      | 3    | any      | A tag that points to an image index (manifest list) with a separate manifest per OS and CPU architecture (`linux/amd64`, `linux/arm64`). The runtime pulls the variant that matches its node. Built on native machines, under QEMU emulation or by cross-compiling.  | The tag is a menu, not an image. An amd64-only image on an ARM node fails with "exec format error"; a multi-platform image lets one name work on both.                                                                                                      | Tags vs digests (the index has its own digest)                          |
| container-registry             | Container registry                         | 1    | any      | A server that stores and serves images in repositories, addressed by tag or digest. | container-tags-vs-digests      | Tags vs digests                            | 2    | any      | A tag (`:1.4`, `:latest`) is a readable pointer that can be moved to a different image. A digest (`@sha256:…`) is the hash of the image manifest, so it always names exactly the same content.                                                                       | `latest` is only a default tag name and doesn't mean newest. Pin images by digest (or use immutable tags) for repeatable deploys. If a tag is re-pushed, Kubernetes' `IfNotPresent` pull policy can leave nodes running different code under the same name. | Image ID; the app's version number                                      |

| k8s-pod                     | Pod                                              | 1    | kubernetes | The smallest unit Kubernetes deploys. A Pod is one or more containers scheduled together on one node. They share a network namespace (one IP, and they reach each other on localhost) and volumes.                                                                                                                                                                       | Kubernetes runs Pods, not containers, and Pods are disposable. | k8s-init-containers         | Init containers                                  | 2    | kubernetes | Containers that run one after another, each to completion, before the app containers start. ### 3.5 Service networking

| k8s-pod-networking   | Pod networking model and CNI                                   | 2    | kubernetes | Every Pod gets its own IP and can reach every other Pod without NAT, on any node.
