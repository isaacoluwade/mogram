# Security & identity: concept catalog

Stage 1 (research) for the Security area. One row per concept; each will later get one animated
diagram. Format and tiers are defined in [`../README.md`](../README.md).

## Scope

**In:** the general ideas behind keeping cloud systems and software secure.

- **Identity and access**: authentication vs authorization, identity providers, SSO, federation,
  SAML, OAuth 2.0 and its flows, OpenID Connect, JWTs, sessions vs tokens, MFA, passkeys,
  conditional access, identity lifecycle, workload identity, RBAC/ABAC/ReBAC, policy evaluation,
  guardrails, privilege escalation, just-in-time and privileged access.
- **Cryptography as practitioners use it**: hashing vs encryption vs encoding, symmetric vs
  asymmetric, signatures, password hashing, PKI and certificates, mTLS, post-quantum, key
  management, envelope encryption, rotation, customer-managed keys, data at rest / in transit /
  in use.
- **Secrets**: vaults, sprawl and leaks, rotation, short-lived credentials.
- **Network security strategy**: zero trust, ZTNA vs VPN, segmentation, WAF, DDoS, bastions.
- **Application and API security**: the OWASP Top 10 (2021 and 2025) and API Security Top 10
  (2023) risks, browser security model (same-origin, CORS, CSP), input/output handling, abuse
  prevention.
- **Secure development and supply chain**: security testing, supply chain attacks, dependencies,
  SBOM, signing, SLSA, CI/CD security, image scanning.
- **Cloud security operations**: audit logging, posture management, policy as code, hardening,
  vulnerability management, threat detection, SIEM/SOAR, incident response.
- **Data protection**: classification, tokenization/masking, DLP, immutable backups.
- **Threats**: threat modeling (STRIDE), the attack lifecycle, phishing, credential attacks,
  lateral movement, ransomware, subdomain takeover. Compliance briefly.

**Left to other areas** (listed under [Overlaps](#overlaps)):

- **Fundamentals**: the shared responsibility model, regions and data residency.
- **Networking**: the TLS handshake itself, firewalls/security groups/NACLs, private endpoints,
  VPN gateways, DNS and DNSSEC, NAT.
- **Containers**: Kubernetes RBAC, pod security, network policies, Kubernetes Secrets, admission
  controllers, service mesh.
- **Data / Reliability**: backup and restore mechanics, disaster recovery, business continuity.
- **Scaling**: rate-limiting algorithms (token bucket and friends). This file owns the _abuse_
  angle only.
- **Observability**: log pipelines, metrics, alerting mechanics. This file owns _audit_ logging.
- **Delivery**: CI/CD and IaC mechanics. This file owns securing the pipeline.
- **AI systems**: prompt injection, agent identity, LLM-specific risks.
- **Git**: signed commits, history rewriting, branch protection.
- **Azure / AWS / Google Cloud**: every named service (Entra ID, IAM roles, Key Vault, KMS,
  GuardDuty, Cloud Armor…). Concepts here are platform-neutral; the platform files explain each
  provider's take.

### 1. Principles, risk and compliance

| --------------------------- | ------------------------------- | ---- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `cia-triad`                 | CIA triad                       | 1    | any      | The three properties security protects: confidentiality (only the right people can read it), integrity (nobody changes it undetected) and availability (it's there when needed).                                 | Every control and every attack maps onto one of the three: exfiltration hits C, tampering hits I, DDoS and ransomware hit A. "What are we protecting, and which property?" comes before "which tool?".           | AAA (authentication, authorization, accounting)                                  |
| `threat-vulnerability-risk` | Threat, vulnerability and risk  | 2    | any      | The vocabulary of risk: a threat (an actor or event) exploits a vulnerability (a weakness) to cause impact; risk is likelihood × impact, and it's treated by mitigating, transferring, accepting or avoiding it. | You can't remove all risk, you rank it. A critical vulnerability nobody can reach may matter less than a medium one exposed to the internet.                                                                     | Vulnerability vs exploit; severity vs risk                                       |
| `least-privilege`           | Least privilege                 | 1    | any      | Give each human, workload and network path only the permissions it needs, for only as long as it needs them.                                                                                                     | Start from nothing and add. Every unused permission is free reach for whoever steals that identity; permissions granted "just in case" are an attacker's gift.                                                   | Need-to-know; zero trust                                                         |
| `defense-in-depth`          | Defense in depth                | 1    | any      | Layering independent controls (identity, network, application, data, monitoring) of different types (preventive, detective, corrective) so one failure doesn't become a breach.                                  | Every layer has holes (the Swiss-cheese model). A breach needs the holes to line up, so you add layers that fail differently, plus detection for when they do line up.                                           | Redundancy for availability; buying more of the same control                     |
| `blast-radius`              | Blast radius                    | 2    | any      | How much an attacker can reach after compromising one credential, workload, account or network segment.                                                                                                          | Assume something will be compromised and design so it reaches as little as possible: separate accounts/subscriptions/projects per environment and workload, narrowly scoped credentials, segmented networks.     | Attack surface (what's exposed before a breach vs what's reachable after)        |
| `fail-secure-defaults`      | Fail secure and secure defaults | 2    | any      | Systems start locked down (private, deny by default) and deny access when something goes wrong: an error, a timeout, a missing policy.                                                                           | An authorization check that times out must mean "deny", not "allow". Unhandled exceptions and fail-open paths are where checks silently disappear (OWASP 2025 A10, Mishandling of Exceptional Conditions).       | Fail-safe (protecting people, e.g. doors unlocking in a fire); high availability |
| `compliance-frameworks`     | Compliance frameworks           | 2    | any      | The landscape of laws (GDPR, HIPAA), standards you certify against (ISO 27001, PCI DSS), auditor attestations (SOC 2) and guidance frameworks (NIST CSF, CIS Controls).                                          | Compliance proves a minimum set of controls existed when audited; it doesn't make you secure. A provider's certifications cover only the provider's side of the shared responsibility line, never your workload. | Being secure; the provider's certifications covering you                         |

### 2. Authentication and identity

| id                                | Concept                                  | Tier | Platform | What it is                                                                                                                                                                                               | The idea to get across                                                                                                                                                                                                                               | Often confused with                                                                          |
| --------------------------------- | ---------------------------------------- | ---- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `authentication-vs-authorization` | Authentication vs authorization          | 1    | any      | Authentication proves who you are; authorization decides what you may do; accounting records what you did.                                                                                               | Signing in once doesn't grant everything: authentication happens at sign-in, authorization must happen on every request. (HTTP 401 means "not authenticated", 403 means "not allowed".)                                                              | Each other; OAuth (authorization) vs OIDC (authentication)                                   |
| `identity-provider`               | Identity provider (IdP)                  | 1    | any      | A central service that holds or connects to the user directory, authenticates users and issues signed assertions or tokens to applications (relying parties).                                            | Applications stop handling passwords. They redirect to the IdP and trust what it signs, so MFA, lockout and offboarding happen in one place.                                                                                                         | Directory (LDAP/Active Directory stores identities; the IdP authenticates and issues tokens) |
| `single-sign-on`                  | Single sign-on (SSO)                     | 1    | any      | One sign-in at the IdP gives the user access to many applications without signing in again.                                                                                                              | The IdP keeps a session and each app silently gets its own token from it. One strong sign-in beats many weak ones, but the IdP account becomes the key to everything, so it gets the strongest MFA.                                                  | Password managers or one password everywhere; federation                                     |
| `identity-federation`             | Identity federation                      | 2    | any      | A trust relationship that lets one organization's or system's IdP vouch for users in another, so they're accepted without separate accounts there.                                                       | Trust is configured once (metadata, signing certificates); after that, the partner checks signatures, not passwords. Federation is how partners, guests, cloud consoles and even CI workloads get in without new credentials.                        | SSO (one IdP, many apps vs trust across domains); directory synchronization                  |
| `saml-sso`                        | SAML single sign-on                      | 2    | any      | XML-based federation protocol: the IdP sends a signed assertion through the user's browser to the service provider (SP).                                                                                 | The browser is only the courier: the SP redirects to the IdP, the IdP authenticates the user and posts a signed assertion back, and the SP trusts the signature. Dominant in enterprise SaaS; awkward for APIs and mobile, which is why OIDC exists. | OpenID Connect (JSON/JWT, API-friendly); OAuth                                               |
| `multi-factor-authentication`     | Multi-factor authentication (MFA)        | 1    | any      | Requiring proof from two or more independent factor categories: something you know, have or are.                                                                                                         | Two passwords is not MFA. Methods differ hugely in strength: SMS codes (SIM swap) < authenticator-app codes (TOTP) < push with number matching < FIDO2 keys and passkeys. Push fatigue and real-time phishing beat the weaker ones.                  | Two-step verification with the same factor; passwordless                                     |
| `passkeys-webauthn`               | Passkeys, FIDO2 and WebAuthn             | 2    | any      | Passwordless sign-in where the device creates a key pair per site; the private key never leaves the device and signs a challenge after a local unlock (biometric or PIN).                                | Nothing reusable is typed or sent, and the signature is bound to the real site's origin, so a look-alike phishing site gets nothing usable. Synced passkeys trade a little assurance for recoverability; device-bound keys are strongest.            | MFA codes (phishable); the biometric being sent to the server                                |
| `conditional-access`              | Conditional and risk-based access        | 2    | any      | Policies evaluated at sign-in or token issuance that combine signals (user, group, device compliance, location, sign-in risk, app) to allow, require MFA or step-up, limit the session, or block.        | Access becomes "if/then" instead of "yes/no": the same user gets in from a managed laptop but is challenged or blocked from an unknown device abroad. This is zero trust's policy engine for identity.                                               | Firewalls and IP allowlists; MFA itself                                                      |
| `identity-lifecycle`              | Identity lifecycle (joiner-mover-leaver) | 2    | any      | Managing an identity from proofing and provisioning, through role changes, to removal; usually driven by HR as the source of truth, provisioned into apps (e.g. via SCIM), with periodic access reviews. | Breaches hide in the transitions: movers keep old access (privilege creep), leavers keep working accounts and tokens. Automated deprovisioning and recurring access reviews close those gaps, for machine identities too.                            | Authentication; one-off account creation                                                     |

### 3. OAuth 2.0, OpenID Connect and tokens

| id                               | Concept                                 | Tier | Platform | What it is                                                                                                                                                                                        | The idea to get across                                                                                                                                                                                                                                                                                          | Often confused with                                         |
| -------------------------------- | --------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `oauth2-delegated-authorization` | OAuth 2.0 (delegated authorization)     | 1    | any      | A framework where a resource owner lets a client app call a resource server's API on their behalf, using an access token issued by an authorization server and limited by scopes and consent.     | The app never sees your password; it gets a scoped, expiring, revocable token. OAuth answers "may this app do X?", not "who is this user?", and consenting to a malicious app (consent phishing) gives it real access.                                                                                          | Authentication/OIDC; API keys                               |
| `oauth-authorization-code-pkce`  | Authorization code flow with PKCE       | 2    | any      | The OAuth flow for apps acting for a user: browser redirect to the authorization server, a one-time code returned to the app, exchanged at the token endpoint together with a PKCE code verifier. | Tokens never travel in the browser URL, and PKCE (the app first sends a hash of a secret, then reveals the secret) makes a stolen code useless. OAuth 2.1 makes PKCE mandatory and drops the implicit and password grants.                                                                                      | Implicit flow (removed); client credentials                 |
| `oauth-client-credentials`       | Client credentials flow                 | 2    | any      | Machine-to-machine OAuth: a service authenticates as itself (secret, certificate or signed assertion) and receives a token for its own permissions, with no user involved.                        | The token represents the app, not a person, so its permissions must be tightly scoped. Prefer certificates, private-key JWTs or federated credentials over shared client secrets that leak and expire.                                                                                                          | Authorization code flow; API keys                           |
| `oauth-device-code`              | Device authorization (device code) flow | 2    | any      | OAuth for input-constrained devices and CLIs: the device shows a short code and URL, the user approves on another device, and the device polls until the token arrives.                           | Sign-in happens on your phone or laptop, not on the TV or terminal. The same feature is its weakness: attackers send victims a genuine device code to approve (device-code phishing), so many organizations restrict the flow.                                                                                  | Authorization code flow; one-time passwords                 |
| `oauth-refresh-tokens`           | Refresh tokens                          | 2    | any      | A long-lived credential the client exchanges at the authorization server for new short-lived access tokens without asking the user to sign in again.                                              | Short access tokens limit damage; the refresh token carries the session, so it's guarded harder: never sent to APIs, rotated on every use, and reuse of an old one signals theft and revokes the whole family.                                                                                                  | Access tokens; session cookies                              |
| `openid-connect`                 | OpenID Connect (OIDC)                   | 2    | any      | An identity layer on OAuth 2.0: alongside the access token the client receives an ID token (a JWT describing the user and the sign-in), plus a UserInfo endpoint and discovery metadata.          | ID token = proof of sign-in for the client app (its audience is the client). Access token = permission to call an API (its audience is the API). Using one in place of the other is a classic bug.                                                                                                              | OAuth 2.0; SAML; access token vs ID token                   |
| `json-web-token`                 | JSON Web Token (JWT)                    | 2    | any      | A compact token of base64url-encoded header and claims plus a signature, used for ID tokens and many access tokens.                                                                               | Signed is not encrypted: anyone can read the claims. Receivers must verify the signature (keys from the issuer's JWKS) and check issuer, audience and expiry. Most JWTs are bearer tokens, usable by whoever holds them until expiry, hence short lifetimes and sender-constrained variants (DPoP, mTLS-bound). | Encryption; opaque session IDs                              |
| `sessions-vs-tokens`             | Sessions vs tokens                      | 2    | any      | Two ways to keep a user signed in: a server-side session referenced by an opaque cookie, or a self-contained signed token validated without a lookup.                                             | Server sessions are easy to revoke but need shared state; self-contained tokens scale but can't be recalled before they expire. Where the browser keeps it matters: HttpOnly, Secure, SameSite cookies resist XSS and CSRF far better than tokens in localStorage.                                              | "JWTs are always better"; cookies vs tokens as transport    |
| `api-authentication-methods`     | API authentication methods              | 2    | any      | How a caller proves itself to an API: API keys, OAuth access tokens, mutual-TLS client certificates, or signed requests (HMAC, cloud request signing, webhook signatures).                        | They prove different things: an API key names a calling app but carries no user or expiry; tokens carry scopes and expire; mTLS proves possession of a private key; request signing proves integrity and blocks replay. An API key is identification, not authorization.                                        | Authentication vs authorization; HMAC vs digital signatures |

### 4. Authorization and privileged access

| id                                  | Concept                                       | Tier | Platform | What it is                                                                                                                                                                                       | The idea to get across                                                                                                                                                                                                                 | Often confused with                                       |
| ----------------------------------- | --------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `role-based-access-control`         | Role-based access control (RBAC)              | 1    | any      | Permissions are bundled into roles, and roles are assigned to principals at a scope (organization, account/subscription/project, resource group, resource).                                      | An assignment is "who + role + where", and it inherits downward through the hierarchy, so a role granted high up silently reaches everything below. Too many fine-grained roles becomes role explosion.                                | ABAC; groups (who) vs roles (what they can do)            |
| `attribute-based-access-control`    | Attribute-based access control (ABAC)         | 2    | any      | Access decided by evaluating attributes of the subject, resource, action and environment (tags, department, time, device state) against policy.                                                  | One rule ("engineers may read resources tagged with their own project") replaces hundreds of role assignments and adapts as attributes change, but whoever can change a tag can change access.                                         | RBAC; conditional access                                  |
| `relationship-based-access-control` | Relationship-based access control (ReBAC)     | 3    | any      | Access derived from a graph of relationships between users and objects (owner of, member of, parent folder of), popularised by Google's Zanzibar and its open-source descendants.                | "Can Alice view this document?" becomes a path search: Alice is in a team that edits a folder that contains the document. It fits sharing-heavy apps that roles can't express, and usually runs as a separate authorization service.   | RBAC; ACLs                                                |
| `default-deny-policy-evaluation`    | Default deny and policy evaluation            | 2    | any      | How authorization engines combine policies: everything is implicitly denied, explicit allows grant access, and an explicit deny overrides any allow.                                             | Effective access is the union of every applicable allow (identity, resource, group, inherited) minus any deny. To debug "access denied", look for the missing allow or the hidden deny.                                                | Firewall rule order (first match wins)                    |
| `permission-guardrails`             | Permission guardrails                         | 2    | any      | Organization-level controls that cap what any identity may do (service control policies, permission boundaries, organization policies, deny assignments), whatever it has been granted.          | Guardrails never grant anything: effective access is the intersection of what's granted and what the guardrail allows. That lets you delegate admin safely ("create roles, but never beyond this ceiling").                            | RBAC grants; policy as code                               |
| `privilege-escalation`              | Privilege escalation                          | 2    | any      | Gaining more access than intended: vertically (user to admin) or horizontally (one user to another), through misconfigured permissions, vulnerabilities or stolen credentials.                   | In the cloud, any permission that can change permissions is effectively admin: creating keys for a stronger identity, attaching a powerful role to compute you control, editing a policy. Hunt for the paths, not just the admin role. | Lateral movement; IDOR (horizontal access inside an app)  |
| `just-in-time-privileged-access`    | Just-in-time and privileged access management | 2    | any      | Replacing standing admin rights with eligible roles activated on demand (MFA, justification, approval) for a limited time, plus vaulted credentials, session recording and break-glass accounts. | Standing privilege is always there for an attacker; JIT privilege exists for one hour because someone asked for it. Separation of duties adds that the requester and the approver are never the same person.                           | Least privilege (how much vs for how long); bastion hosts |

### 5. Workload identity and secrets

| id                             | Concept                              | Tier | Platform | What it is                                                                                                                                                                                      | The idea to get across                                                                                                                                                                                                                                               | Often confused with                                                                                               |
| ------------------------------ | ------------------------------------ | ---- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `managed-workload-identity`    | Managed workload identity            | 1    | any      | The platform gives a workload (VM, function, container) its own identity and serves it short-lived tokens from a local metadata endpoint, so code calls cloud APIs without any stored secret.   | No secret to leak, rotate or commit: the credential is fetched at runtime and expires in minutes. It also answers "secret zero" (how does the app authenticate to the vault?). Machine identities far outnumber humans, so this is the default to reach for.         | Service-account keys or client secrets; API keys                                                                  |
| `workload-identity-federation` | Workload identity federation         | 2    | any      | Workloads outside a cloud (CI pipelines, Kubernetes clusters, other clouds, SPIFFE) exchange their own platform-issued OIDC token for short-lived cloud credentials through a configured trust. | The cloud trusts an external issuer for specific subjects (this repo, this branch, this service account) instead of you storing a long-lived key in CI. The trust condition is the security: too broad, and any repository on that platform can assume your role.    | Managed identity (inside the cloud); federation for humans                                                        |
| `secrets-vault`                | Secrets management vault             | 1    | any      | A central service that stores secrets (passwords, API keys, connection strings, certificates) encrypted, access-controlled, versioned and audited, and hands them to apps at runtime.           | Secrets live in one place and are pulled at runtime by an authenticated identity, so you know who read what, can rotate centrally and revoke fast, instead of hunting copies across configs.                                                                         | Key management service (KMS keeps keys and does crypto; a vault stores and returns values); environment variables |
| `secret-sprawl`                | Secret sprawl and leaked credentials | 2    | any      | Secrets copied into source code, env files, CI variables, container images, logs, tickets and chat, where nobody can track them and they leak easily.                                           | Cloud keys pushed to public repositories are found by automated scanners within minutes and abused (often for crypto-mining). Deleting the commit doesn't help, because history and forks keep it: revoke and rotate, then add secret scanning with push protection. | Secrets management (the fix); encryption                                                                          |
| `secret-rotation`              | Secret rotation                      | 2    | any      | Replacing secrets on a schedule and immediately on suspected exposure, ideally automated by the vault.                                                                                          | Zero-downtime rotation needs overlap: create the new secret, roll it out, switch over, then revoke the old one. Systems built for exactly one valid secret break on rotation day.                                                                                    | Key rotation (versioned keys; old versions kept to decrypt)                                                       |
| `short-lived-credentials`      | Short-lived and dynamic credentials  | 2    | any      | Credentials generated on demand with a short time-to-live (temporary security tokens, per-request database users, signed URLs) instead of long-lived static ones.                               | A credential that expires in 15 minutes is a small problem when it leaks, and there's nothing to rotate. The catch: the caller needs an identity to request them, which leads back to workload identity.                                                             | Secret rotation; session tokens                                                                                   |

### 6. Cryptography

| id                                   | Concept                                      | Tier | Platform | What it is                                                                                                                                                                                 | The idea to get across                                                                                                                                                                                                                                                       | Often confused with                                                                   |
| ------------------------------------ | -------------------------------------------- | ---- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `hashing-vs-encryption-vs-encoding`  | Hashing vs encryption vs encoding            | 1    | any      | Encoding changes format and anyone can reverse it (Base64); encryption hides data and only the key reverses it; hashing produces a fixed-size, one-way fingerprint.                        | Base64 is not security. Encrypt when you need the data back; hash when you only need to compare or detect change (integrity checks, password verification).                                                                                                                  | Each other; compression                                                               |
| `symmetric-vs-asymmetric-encryption` | Symmetric vs asymmetric encryption           | 1    | any      | Symmetric uses one shared key (fast; e.g. AES). Asymmetric uses a key pair: the public key encrypts or verifies, the private key decrypts or signs (slow; e.g. RSA, elliptic curves).      | Real systems use both: asymmetric crypto to agree on or deliver a symmetric key (as TLS does with Diffie-Hellman), then symmetric crypto for the bulk data. The hard problem is always distributing keys safely.                                                             | Public key = certificate; signing vs encrypting                                       |
| `digital-signatures`                 | Digital signatures                           | 2    | any      | Hashing data and signing the hash with a private key, so anyone holding the public key can verify who signed it and that it hasn't changed.                                                | Signing proves origin and integrity (and non-repudiation); it hides nothing. Signatures underpin certificates, JWTs, code signing and package signing.                                                                                                                       | Encryption; HMAC (shared secret, so no non-repudiation)                               |

| `lateral-movement`                 | Lateral movement                                       | 2    | any      | After the first foothold, moving to other machines, accounts and environments with stolen credentials and tokens (pass-the-hash, reused admin passwords, role chaining, identities synced from on-premises to cloud).             | The first compromised machine is rarely the target. | `ransomware`                       | Ransomware attack chain                                | 2    | any      | Extortion attacks: initial access (phishing, exposed remote access, unpatched edge devices), escalation, disabling backups, exfiltrating data (double extortion), then encrypting systems or cloud data.                          | Encryption is the last step of a long chain, so there are many chances to catch it earlier. | `subdomain-takeover`               | Subdomain takeover (dangling DNS)                      | 3    | any      | A DNS record still points at a cloud resource (app, storage endpoint, CDN) that was deleted, so an attacker creates a resource with the same name and serves content on your domain.                                              | Cloud resource names get recycled; DNS records don't clean themselves up.
